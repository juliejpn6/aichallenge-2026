gate3「車線維持（ピットレーン走行）」課題まとめ

車庫発進 → 極狭ピットレーンの低速走行 → コースイン。課題・原因・対処・改善の記録。

1. 概要

gate3 は、車両がレースライン上ではなく車庫（ピット）でスポーンし、 極端に狭いピットレーン（最狭 約2.5m、車幅1.45m）を低速で走り抜けてコースインする課題。 当初は発進すらできず、その後もピット出口の右壁に繰り返し衝突していた。

設計上の制約として、gate3 専用にせず gate1 / gate2 / gate3 / make eval すべてで動く統一実装とすること、 スポーン座標で参照経路を判別し、コースインしたらレースラインへ切り替える（切替は GNSS 座標で）こと、を満たす必要があった。

2. どのような課題だったか

① 発進しない
既定の MPC はレースライン（traj_mincurv.csv）を追従する設定。だが gate3 の発進地点はレースラインから 約10m離れた車庫。経路に乗れず目標速度が出ず、v=0 のまま動かない。
② 右壁に衝突
発進できるようにした後も、発進直後に右へ操舵し、ピット出口の右壁へまっすぐ流れて衝突。 対策を変えても同じ場所で当たり続けた（最難関）。
③ コリドー崩壊（infeasible）
回避コリドーが「No feasible free segment」で崩壊し、MPC が解けず無操舵で壁へ。
④ 統一実装の要求
gate3 専用ロジックは不可。発進座標で経路を自動判別し、コースインで自動復帰する汎用設計が必要。

3. 原因究明のタイムライン（試行錯誤の記録）

発進不可
原因：参照がレースラインのみ。車庫はそこから約10m。 → 対処：発進座標でピット経路(from_garage)を読む機能を追加。
コリドー崩壊（infeasible）
原因：占有格子地図がピット/車庫を全面「占有」として持つため、回避コリドーが空きを見つけられず崩壊。 → 対処：ピット内は回避OFF（純経路追従）。
誤診A：低速ヨー＝自己位置失敗（撤回）
「低速でヨーが乱れる」と誤診し最低速度を追加 → 改善せず壁へ。再解析で 衝突後のアーティファクトと判明し撤回・謝罪。
誤診B：spawnアンカー経路（撤回）
経路先頭をスポーンに合わせ徐々に from_garage へ戻す案 → むしろ収束を遅らせ右へ流す逆効果。撤回。
突破口1：占有格子は不正確、lanelet2 に真の壁がある
占有格子はスポーン地点すら「占有」なのに車は走れる＝ピットでは信用できない。 一方 lanelet2 地図にピットレーン境界（relation 9747 / 左 way 9746・右 way 9743）が同一座標系で定義されており、 実際の AWSIM 壁と±0.3mで一致。これが壁の真値。
突破口2：EKF方位が低速で約17°ずれる（真の主因）
GNSS軌跡の実方位と EKF方位を比較すると、ピット全域で EKF が +15〜19°（左に）ずれていた。 MPC は「レーンに合わせるには右へ」と誤判断し右へ操舵し続け右壁へ。 EKF方位はレース速度では収束するが低速(<0.9m/s)では収束せず。位置も約0.45mずれていた。

4. 根本原因（確定）

主因：低速での自己位置（EKF）誤差
  • 方位（heading）が約 +15〜19° ずれる：MPC の横方向予測 e_y′ は方位 e_psi に依存するため、 方位が誤っていると「この操舵で十分」と誤予測し、実際は右へ流れる。 ハード制約すら予測誤差で破られる。
  • 位置が約 0.45m 壁側にずれる：MPC は「ライン上にいる」と誤認し補正が効かない。
  • いずれも低速特有（レース速度では GNSS 速度で EKF が収束するため gate1/2/レースは無影響）。
副因：占有格子地図がピットを表現していない
ピット領域は地図上「全面占有」。回避コリドーも壁制約も機能しない。 壁の真値は lanelet2 地図（ピットレーン境界）にあった。
補足：from_garage 基準線はレーン中央でなく右寄り
狭部で参照線が右境界寄り。Q[e_psi] 支配で参照に平行な右オフセットを保ち、右壁へ張り付きやすい。

5. どのような対処を行ったか（最終解＝多層構成）

いずれも mpc_controller.py と config.yaml のみで実装（CSVは不変）。 on_pit（ピット走行中）でのみ作用し、gate1/2/レースには影響しない。

A. 統一ピット機能（発進座標で自動判別）
発進時、レースラインまでの距離で判別：遠ければ（車庫/ピット）from_garage 経路、近ければレースライン。 走行中、レースラインに十分近づいたら（コースイン）レースライン（周回）へ一度だけ切替。 → gate1/2/3/eval 共通で動作。ピット内は回避OFF。
B. ピット内のみ GNSS 位置で自己位置補正
on_pit 時、MPC の pose.x/y を GNSS 実測へ置換。 → 低速で生じる EKF の約0.45m横ずれを解消。
C. ピット内のみ GNSS 軌跡から実方位を算出（主因への対処）
GNSS pose は方位が無効（identity）のため、直近約0.4mの GNSS 位置履歴から進行方位を算出し pose.theta に使用。→ EKF方位の約17°誤差を解消。位置・方位とも GNSS で自己整合。これが決定打。
D. lanelet2 ピット境界を MPC のハード壁コリドーに使用
不正確な占有格子の代わりに、lanelet2 のピットレーン左右境界（way 9746/9743）から各 waypoint の ub(左)/lb(右) を算出。MPC はコリドー中央を横目標にしつつ e_y を壁内にハード拘束。 ピット専用マージン safety_margin_pit = 0.9m（既定の 1.63m は最狭部でコリドー崩壊するため）。 → 最狭レーン2.48mでもコリドー≥0.68m（feasible）。参照線の横位置に依存せず中央を走る。
E. ピット横追従の重みを強化
q_ey_pit を 5e6 → 5e7。狭部で Q[e_psi]=1e8 に対抗してレーン中央へ確実に寄せる （右張り付きの解消）。→ 左壁側はコリドーがハード制約で守るため安全。

9. 教訓

  • 症状（右壁衝突）だけで原因（EKF方位誤差）は分からない。位置・方位・予測の各層をログで切り分けることが決定的だった。
  • 地図ソースの妥当性を疑う：占有格子はピットで不正確。lanelet2 が真の壁を持っていた。「壁が分からない」のではなく見る地図を間違えていた。
  • ハード制約も予測モデルが間違っていれば破れる：方位（e_psi）が誤ると e_y 予測が崩れ、コリドー制約が機能しない。
  • 低速は別物：EKF方位はレース速度で収束するが低速では収束しない。ピット専用に GNSS 由来の自己位置で整合させた。
  • 誤診を 2 度行った（低速ヨー / spawnアンカー）。データで反証して撤回し、最小変更で積み上げた。

10. 補足・今後

  • ピット中盤に約5秒の停止が見られたが、前進指令が出ているのに静止＝gate3 仕様の必須ピットストップと判断（許容）。
  • ピット出口の加速をより滑らかに（広い出口区間で速度上限をランプアップ）する改善余地あり。
  • 本課題で確立した「GNSS 由来の自己位置整合」と「lanelet2 を壁の真値として使う」手法は、 今後の追従精度向上・オーバーテイク経路の正確トレースにも応用できる。
