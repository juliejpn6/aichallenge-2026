# OSQPウォームスタート履歴依存の除外検査(2026-08-03、Phase2)

目的: Part C(Q×v_max 2×2実験)の条件間比較が、OSQPのウォームスタート履歴(直前周期からの解の引き継ぎ)の差で汚染されないことを確認する交絡除去。241節根本対処候補④(OSQPウォームスタートの履歴依存性検証)にも対応する。

## 確認1: OSQPの収束設定はデフォルトのまま(緩められていない)

`core/MPC.py`の`.setup()`呼び出し(441行目・501行目)を確認したところ、`eps_abs`/`eps_rel`/`max_iter`は明示的に指定されておらず、OSQPのデフォルト値がそのまま使われている:

```
eps_abs  = 0.001
eps_rel  = 0.001
max_iter = 4000
```

## 確認2: 極端なウォームスタート初期値でも解の差は収束許容誤差の範囲内

MPC.pyの実際の問題規模(nx=4[delta_actual込み]・N=20・nu=2 → 変数数 = nx×(N+1)+nu×N = 124)と同程度の凸QP(半正定値P、制約数100)をランダム生成し、(a)ゼロ初期化(コールドスタート相当)、(b)通常あり得ない極端に大きい初期値(スケール1000)、の2パターンでOSQPに解かせて比較した。

| 条件 | ステータス | 反復回数 |
|---|---|---|
| (a) ゼロ初期化 | solved | 175 |
| (b) 極端な初期値(scale=1000) | solved | 100 |

**両者の解ベクトルの最大絶対差: `3.03e-4`** — これはOSQPの収束基準(eps_abs=eps_rel=1e-3)の範囲内であり、Part Cで比較する操舵角(度単位、通常の変動幅は数度〜十数度)に対して無視できる誤差(約0.017度相当)である。

## 確認3: 既存コードは既にウォームスタート汚染への意識的対処を持つ

`MPC.solve()`のinfeasibleリトライロジック(642-675行目)は、最終リトライ段の前に`reset_solver_state()`(ウォームスタートをゼロクリア)を呼んでおり、コメントに「悪い初期点を引きずったままの反復増加(交通が濃い局面でのretry再肥大の一因)を防ぐ」と明記されている。つまり、ウォームスタート起因のリスクは既に一部設計上考慮済みである。

## 結論: Part Cの条件間比較を汚染するリスクは低い

理論(凸QP + 十分な収束基準)と実証実験の両面から、**ウォームスタート履歴の違いがPart Cの条件間比較(C-1〜C-4)を汚染するリスクは低い**と判断する。条件間で追加のリセット手順(ノード再起動等)を講じる必要性は薄い。

## 正直な限界

- 検証は「MPC.pyの実際の問題構造(コリドー制約・車両動特性)」ではなく、**同規模・同程度の凸性を持つランダムなQP**での実証実験に留まる。reference_path等の完全な依存関係(占有格子マップ含む)を使ったフルのMPCインスタンスでのend-to-end検証は、実装コストの制約により今回実施していない。
- OSQPが`solved`ステータスを返す限り上記の結論は妥当だが、もし実際の走行でinfeasibleが頻発する局面(リトライが多発する場面)では、既存の`reset_solver_state()`による意図的なクリアが働くため、むしろウォームスタートの影響はそちらで別途管理されている。
- より厳密な検証が必要になった場合、reference_path込みのフルMPCインスタンスを構築して同種の実験を行う価値はある(今回は見送り)。
