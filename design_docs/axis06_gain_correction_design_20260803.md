**2026-08-03続報(仮説の棄却、実地検証で判明)**: 提出前にユーザー判断でローカルA/Bを
先に実施(v_max=20km/h・Q=700k・delay=0.055、C-1と同一条件でgainのみ0.67に変更)。
1周目のekf_ey範囲(-1.67〜+1.38m)はC-1基準(-1.67〜+1.32m)とほぼ同水準で、数値上の
劇的な悪化は見られなかったが、**ユーザーの目視観察で「最初の舵角が計画経路に対して
大きく、切りすぎているように見える」「ハンドル操作開始と同時に蛇行が始まる」との
報告があった**。

**結論**: もし実際のアクチュエータが真にゲイン0.67(指令の67%しか実現しない)であれば、
本補正(指令を約1.49倍に拡大)は正しく効き過剰操舵にはならないはずである。「切りすぎ」
という直接観察は、**実際のアクチュエータはゲイン≈1(指令にほぼ忠実)であり、
`estimate_gain_continuous`が測定した「0.67」は真のゲイン不足ではなく、振動する信号
(0.6-0.7Hzの限界サイクルそのもの)に対して、tau/位相がわずかにずれた予測波形を基準に
回帰したことで生じる、統計的な減衰(attenuation)アーティファクトだった可能性が高いこと
を示唆する**。振動信号を位相のずれた基準と回帰すると、真のゲインが1であっても見かけ上
小さく出るという、システム同定における既知の落とし穴に該当すると考えられる。

**対処**: `actuator_gain`を1.0(無効)へ復元し、config.yaml・debug_extra_actuator_delay_s
も安全な状態(0.0)へ戻した。**緩和策①(大舵角ゲインの内部モデル化)は棄却する**。
Phase1出口ゲートの「緩和策選定」は再検討が必要(tau修正、またはゲイン測定手法自体の
見直し[振動除去後の静的ステップ応答での再測定等]が次の候補)。

## 緩和策②: tau修正(190ms→160ms、2026-08-03)

`analyze_actuator_delay.py`のFOPDT実測(v_max=15/20km/h×Q=700k/1.0Mの4条件中3条件で
tau=160ms一致)に基づき、`actuator_lag_tau_s`のPythonデフォルトを0.19→0.16へ変更
(213節と同じ手順: デフォルト値変更+関連テスト更新)。回帰スイート3013件全PASS。

### ローカルA/B結果(v_max=20km/h・Q=700k、C-1と比較)

| 条件 | 平均初期振幅 | 平均対数減衰率 | ringing判定 | hotspot p95\|ekf_ey\| | hotspot判定 |
|---|---|---|---|---|---|
| C-1(tau=190ms、基準) | 8.27° | 0.63 | FAIL | 1.53m | FAIL |
| tau=160ms・delay=0.055 | 9.20°(やや悪化) | **0.88**(大幅改善) | FAIL(僅差) | **0.66m** | **PASS** |
| tau=160ms・delay=0.060 | 9.08°(やや悪化) | 0.48(悪化) | FAIL | **0.67m** | **PASS** |

**発見**: tau=160msへの変更で、wp269-282ホットスポットは両delay値で明確にPASSへ転じた
(p95|ekf_ey| 1.53m→0.66-0.67m)。一般ringingは初期振幅がやや悪化する一方、対数減衰率は
delay=0.055で大幅改善(0.63→0.88、合格ライン0.9に肉薄)したが、delay=0.060では逆に悪化
(0.48)した——**わずか5msのdelay差で結果が大きく変わるほど感度が高い**(213節のtau感度の
高さと同様の傾向)。ユーザーの目視観察(「S字後のハンチングが大きい」「直線・ヘアピンの
組み合わせは改善」)と数値結果は一致した。

**結論**: ゲイン修正(棄却)とは対照的に、tau修正は方向性として改善に働いている
(特にwp269-282ホットスポットの完全解消)。ただしdelay値への感度が高く、単一のn=1試行
では最適値を確定できない。tau=150ms等の追加候補・複数試行での再現性確認が必要。

### tau=150msの追加検証+L_eff_localのtau非依存性の確認

ユーザーの鋭い指摘(「tauを変えたら注入すべきdelayも変わるのでは」)を受け、まずtau=160ms・
delay=0でL_eff_localを再測定したところ、**180ms(旧tau=190ms時と完全一致)**だった。
これは`debug_extra_actuator_delay_s`(実際に公開するコマンドを遅らせる、本物の追加むだ時間)
と`actuator_lag_tau_s`(MPC内部予測モデルのみに使われ、実際のAWSIM車両の物理応答には
影響しないパラメータ)が性質の異なる量であることの直接的な証拠であり、**既存較正
(delta=55-60ms)はtauの値に依らず有効**と確認できた。

この確認の後、tau=150ms・delay=0.055でも6周検証した。

| 指標 | C-1(tau190、基準) | tau160_delay055 | tau150_delay055 |
|---|---|---|---|
| 平均初期振幅 | 8.27° | 9.20° | 7.67°(3条件中最良) |
| 平均対数減衰率 | 0.63 | 0.88(3条件中最良) | 0.76 |
| ringing判定 | FAIL | FAIL(僅差) | FAIL |
| hotspot p95\|ekf_ey\| | 1.53m | 0.66m(3条件中最良) | 1.34m |
| hotspot判定 | FAIL | PASS | PASS(僅差) |

**発見**: tau150とtau160のどちらが優れているかは指標によって逆転し、単調な関係ではない
(150msは振幅最良、160msは減衰率・hotspot最良)。n=1試行/条件のため、この非単調性が
真の現象か試行間ノイズかは未確定。ただしいずれも190ms基準よりhotspot判定はPASS方向へ
改善しており、**tau短縮(190ms→150-160ms)という方向性自体は一貫して有効**と考えられる。

### tau×Q交互作用の確認+最終決定(2026-08-03)

Q=1.0M(tau=160ms)も追加検証したところ、Part Cで見られた「Qを上げるとhotspotが悪化する」
トレードオフはtau修正後も変わらず成立した(hotspot p95|ekf_ey| 0.66m→1.87m、C-1基準の
1.53mより悪化)。tau150×Q1.0Mは傾向から明確に不利と判断し未実施。

**最終決定**: tau=160ms・Q=700k(現行維持)を採用。config.yamlはこの組み合わせに対応する
状態(v_max=20.0・Q=700k・actuator_gain=1.0[無効]・debug_extra_actuator_delay_s=0.0
[競技提出用])に整えた。**今回の実質的な変更はtau=190ms→160msのみ**(Python既定値、
config.yaml非依存)。予選環境での検証へ進む。

### 予選環境での実地検証結果(0804-01、2026-08-04): 期待した改善は再現せず

| 指標 | 0803-03(旧tau190基準) | 0804-01(新tau160) |
|---|---|---|
| 平均初期振幅 | 8.49° | **12.00°(悪化)** |
| 平均対数減衰率 | 0.67 | 0.87(改善) |
| ringing判定 | FAIL | FAIL |
| hotspot stall_rate | 22.2% | 14.3%(改善) |
| hotspot p95\|ekf_ey\| | 1.93m | **2.18m(悪化)** |
| hotspot判定 | FAIL | FAIL |

ユーザーの目視観察(「特に改善している様子は見られなかった」)と一致。ローカルA/B
(tau160・delay=0.055、対戦車なし)で見られた明確な改善(hotspot PASS、p95|ekf_ey|
1.53→0.66m)は、実際の予選環境(対戦車との相互作用込み)では再現しなかった。
STEER-XCORRのlag_ms分布は大部分(88%)が150-225msで既知の基準と整合しており、
実効遅延自体の異常悪化は確認されなかった(400msの外れ値は全体の4.6%程度、
STUCK復帰等のイベント起因と推測)。

**解釈**: ローカルA/Bはn=1試行・対戦車なしの単純化条件であり、実際の予選環境は
対戦車との相互作用(オーバーテイク・回避)が支配的で、tau修正単体の効果がその中に
埋もれた可能性が高い。またローカルでもtau=150/160msで非単調な結果が出ていたことから
(前述)、tauの効果自体が試行間ノイズの範囲内である可能性も排除できない。**tau修正
(190ms→160ms)だけでは、実環境での蛇行を明確に改善するには不十分**という結論に至った。

### 振動周波数の理論的裏付け(2026-08-03)

積分器(heading、-90°固定)+一次遅れ(アクチュエータ、tau)+純遅延(残差L)の合計位相遅れが
-180°になる周波数(位相交差周波数)を計算したところ、tau=160-190ms・L=180-240ms
(既存のL_eff実測値)の組み合わせで**予測周波数0.62-0.75Hz**となり、実測されている
限界サイクル周波数帯(0.6-0.7Hz)とよく一致した。これは遅延+一次遅れ+高ゲイン
(Q[e_psi]=100M、heading誤差への強い修正)という機構仮説を、周波数という独立した指標
からも裏付けるものである(簡易モデルであり、MPCのQP自体の挙動は含まない近似)。

## 背景(選定に至った実測根拠)

1. Part C 2×2実験(`corner_ringing_offset_dynamics_20260803.md`)で、蛇行の支配因子は
   v_max(Q[e_y]ではない)と確定。v_max=15km/hはQ700k/1.0Mどちらも合格基準PASS、20km/hは
   どちらもFAIL。
2. tau実測(`analyze_actuator_delay.py --mode steering`)で、FOPDT tau=160msがv_max・Qに
   依存せず一定と確認。速度依存の悪化はtau(時定数)の変化では説明できない。
3. ゲイン実測(同ツールの`estimate_gain_continuous`拡張)で、通常走行域(|指令振幅|0-30°)の
   ゲインが4条件すべてで**0.63-0.78(既知値0.67と整合)、舵角の大きさにほぼ依存せず一定**と
   判明。MPCの内部モデルは「delta_actualは指令deltaへゲイン1で収束する」と仮定しているが、
   実際は約0.67-0.7でしか収束しない——**この一定のゲイン不一致が、速度が上がるほど1周期
   あたりの補正不足を拡大させ(進む距離・必要な横加速度がともに速度とともに増えるため)、
   蛇行として顕在化する**、というのが現時点の統合的な機構仮説。

## 現状のモデル(`core/spatial_bicycle_models.py`、`BicycleModel`)

delta_actual(第4状態、201節続報のAXIS06拡張)の連続時間ダイナミクスは:

```
d(delta_actual)/dt = (delta - delta_actual) / tau
```

これは定常状態でdelta_actual→delta(**ゲイン=1**)に収束することを前提にしている。
線形化(`linearize()`)では、離散化率`alpha = clip(delta_s/(tau*v_ref), 0, 1)`を使い:

```
delta_actual_{k+1} = (1-alpha)*delta_actual_k + alpha*delta_k   (a_4, b_4行)
```

e_psiの更新(a_2, b_2行)も、delta_actual_{k+1}経由でdeltaの寄与を受け取る設計になっている
(203節続報のバグ修正で、delta_actual_kでなくdelta_actual_{k+1}を使うよう修正済み)。

## 提案: ゲインパラメータ`actuator_gain`の追加

新規パラメータ`actuator_gain`(既定1.0、下位互換)を導入し、連続時間モデルを:

```
d(delta_actual)/dt = (actuator_gain * delta - delta_actual) / tau
```

へ変更する。定常状態でdelta_actual→actuator_gain*delta(実測ゲイン0.67-0.7を反映)に収束する。

### 具体的な変更箇所(設計、未実装)

1. `BicycleModel.__init__`: `actuator_gain=1.0`パラメータを追加(既存の`actuator_lag_tau_s`と
   同じ扱い)。`self.actuator_gain = actuator_gain`。
2. `get_spatial_derivatives()`: `d_delta_actual_d_s = (self.actuator_gain * delta - delta_actual) / (tau * s_dot)`
   (`delta`の係数にactuator_gainを掛けるのみ)。
3. `linearize()`:
   - `b_4 = np.array([0, alpha * self.actuator_gain])` (元は`[0, alpha]`)
   - `b_2 = np.array([0, delta_s * alpha * self.actuator_gain])` (元は`[0, delta_s * alpha]`)
   - `a_2[3]`(delta_actual_kの係数、`delta_s * (1 - alpha)`)は**無変更**
     (前ステップの状態の持続には影響しないため)
   - `a_4`(delta_actual_kの係数、`1 - alpha`)も**無変更**

### 下位互換性

`actuator_gain=1.0`を指定すると、上記全ての変更箇所で乗算が1倍になり、既存モデルと
数学的に完全一致する。既存のtau=0.0(delta_actual_next=delta_cmd即時追従)との組み合わせ
(actuator_gain=1.0・tau=0.0)でも、旧3状態モデルとの完全一致は保たれる。

## 想定するconfig値

実測ゲイン(通常走行域、4条件平均)は0.63-0.78の範囲でばらついた。単純平均は約0.70。
既存の`awsim-steering-actuator-limits`メモリの実測値(0.67)により近い保守的な初期値として
`actuator_gain=0.67`を推奨する。QP側の`delta_max_deg`等、既存の舵角制約とは独立したパラメータ
であり、混同しないよう注意する。

## 正直な限界

- ゲイン実測は舵角振幅ベースの回帰であり、速度・横滑り角・タイヤ荷重移動等、他の要因による
  非線形性を切り分けられていない可能性がある。
- 極端域(30-90°、主にSTUCK-PUSH由来)でのゲイン低下(0.27-0.61)は本設計では扱わない
  (通常走行の蛇行対策としての優先度が低いと判断したため)。将来的にPUSH復帰動作自体の
  ゲイン特性が問題になった場合は、別途対処が必要になる可能性がある。
- 本設計は未実装・未検証であり、Phase2でのローカルA/B検証(上記4)が必須。
