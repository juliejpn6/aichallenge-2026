# V2X異常時の防御穴検査(2026-08-03、Part2)

コード読みのみ。制御ロジックの変更は行っていない。

## 訂正: 前回報告した`vopp`の解釈ミス

[[v2x-d2-speed-anomaly-collision-suspected-0803]]で報告した際、0803-02の`[OT]`ログの
`vopp=10.7〜13.5`を「m/sで物理的にありえない値」としたが、これは誤りだった。
`mpc_controller.py:5822`で `_fwd_dbg["vopp"] = round(_fwd_vopp * 3.6, 1)` と**km/h単位に
変換してログ出力**しており、正しくは2.97〜3.75 m/s(10.7〜13.5 km/h)で物理的に正常な値
だった。V2Xクランプの継続発生(前回比4.7-6.2倍)自体、COLLISION-SUSPECTEDの発生自体、
実車速の急落自体(m/s単位で確認済み)は訂正の対象ではない — 誤っていたのは「vopp」の
単位の解釈のみ。

## 検査1: クランプ時の速度は下流で「0扱い」か「直前値保持」か

**「0扱い」である**(`v2x_vehicle_tracker.py:65-69`):
```python
if math.hypot(vx, vy) > self._v_max_safety:
    self._velocities[vid] = (0.0, 0.0)
```
直前の有効値を保持する仕組みはない。以降`velocity(vid)`は次の有効な更新まで`(0.0, 0.0)`を
返し続ける。

**下流での扱い(3箇所を確認)**:

1. **heading計算**(`mpc_controller.py:2669-2676`): `np.hypot(vx,vy) >= opp_obstacle_speed`
   が偽になるため、速度ベクトルではなく**参照経路接線(track_tangent)へ安全にフォールバック**
   する設計が既にある。これはコメントより「速度ベクトルが信頼できない停止/低速車向け」に
   意図的に用意されたものであり、クランプ時もこの安全側フォールバックの恩恵を受ける。
   **この経路に穴は無い。**

2. **fwd_vopp(closing判断に使うscan値)**(`mpc_controller.py:3111-3112`):
   `v_long = max(0.0, vx*cos(psi) + vy*sin(psi))` — クランプ時は`vx=vy=0`のため`v_long=0`
   になる。これが`_ego_ready`判定・`_closing_est`計算(`mpc_controller.py:2892-2896`)に
   そのまま使われる:
   ```python
   _closing_est = (self._v_pot - opp_sit.fwd_vopp) if opp_sit.fwd_vopp is not None else self._v_pot
   ```
   **fwd_vopp=0は「相手が完全停止」を意味し、closing_estが実際の相対速度より過大評価される
   (自車が実際より速く追いつけると誤判定する)方向に倒れる。** これは「クランプで相手を
   見失う」方向ではなく「クランプで相手を停止車と誤認し、追い越し判断を積極化させる」方向
   の穴であり、依頼にあった懸念(真横の動いている相手を静止扱いする)と整合する実在の穴と
   判断する。

3. **位置予測(predictions)**(`v2x_vehicle_tracker.py:85-93` `predict_positions`):
   `x_last + vx*t` の等速外挿のため、クランプ時(vx=vy=0)は**静止予測**になる。ただし
   `mpc_controller.py:2704-2709`で、対象wpに学習済みの`opp_map`データがあれば
   `_opp_predict_along_path`で置き換えるセーフティネットが既にある。**学習済み区間では
   この穴は実質塞がっている。未学習区間(1周目、または学習データが疎な区間)では静止予測が
   そのままコリドー生成(`predictions_to_obstacles_capsule`)に渡り、コリドーが「相手は
   動かない」前提で計算されるリスクが残る。**

**0803-02実データでの裏付け**: COLLISION-SUSPECTED発生時刻(wp_id=139)の直前、V2Xクランプ
(d2)が13Hz周期で継続していた。同時刻の`[OT]`ログで`fwd_dlat=3.49m`(横方向は計画上十分な
余裕)だったにもかかわらず速度が実際に急落していることから、closing_est過大評価による
「早すぎる/詰めすぎたOVERTAKING判断」が寄与した可能性は否定できないが、n_dynobs=0(下記)
と同時発生しているため、この1件だけから穴2(fwd_vopp=0)単独の因果を断定はできない。

## 検査2: `n_dynobs`瞬断時の扱い

`n_dynobs`(`self._dbg_n_dynobs`、`mpc_controller.py:5325`)は`filtered_dynamic`
(`_dynamic_obstacles`をコリドー近傍でフィルタしたもの)の件数。`_dynamic_obstacles`は
`_v2x_callback_impl`内で構築され、**速度クランプそのものは`ds`(縦距離)計算に直接影響しない**
(`ds`は位置`(cx,cy)`のみから計算されるため)。

`n_dynobs`が0へ落ちる主因は、`mpc_controller.py:2712-2722`の位置ベースのヒステリシス除外
と考えられる:
```python
thr = -self._rear_map_exit if prev else -self._rear_map_enter
thr_f = self._fwd_map_exit if prev else self._fwd_map_enter
inc = (thr < ds < thr_f)
if not inc:
    del predictions[vid]
```
0803-02のCOLLISION-SUSPECTED時点で`d_min(=fwd_ds)=0.0`(ちょうど真横、rear/fwdの境界)
だったことから、**真横通過の瞬間に`ds`が`rear_map_enter=0.5m`のヒステリシス境界をまたぎ、
一時的に除外された可能性が高い**。これは速度クランプに起因する穴ではなく、**既存の
enter/exitヒステリシス設計が想定する「境界をまたいだ瞬間の一時除外」という、意図された
(ただし副作用のある)動作**と考えられる。

**例外処理によるフォールバック**: 2650-2724行目は`try/except Exception: pass`で囲われて
おり、コメント通り「起動直後(wp未確定)等は全車保持=従来挙動にフォールバック」する。
ただし今回のn_dynobs=0は例外発生ではなく、`inc`条件の正常な評価結果であるため、この
フォールバックの対象外である。

## 結論: 穴の実在有無

| 検査対象 | 穴の実在 | 根拠 |
|---|---|---|
| ①クランプ時のheadingフォールバック | **無し**(既に安全側設計) | track_tangentへの既存フォールバック |
| ②クランプ時のfwd_vopp=0によるclosing過大評価 | **あり** | 相手を停止車と誤認し追い越し判断を積極化させうる |
| ③クランプ時の静止予測(未学習区間) | **部分的にあり** | 学習済み区間はセーフティネットあり、未学習区間は静止予測のまま |
| ④n_dynobs瞬断 | **既存設計の副作用**(速度クランプ起因ではない) | ds境界のヒステリシスによる一時除外 |

## 修正設計案(実装はしない、人間の確認後に別タスクで)

1. **穴②③への対応(優先度高)**: `V2XVehicleTracker`にクランプ発生時、速度を即座に
   `(0.0, 0.0)`にする代わりに「直前の有効速度をN周期(例: 3-5周期、鮮度タイムスタンプ付き)
   保持し、それ以降のみ0へ減衰させる」設計を検討する。既存の`is_settled()`(窓が満杯かの
   判定)と同様の仕組みで、「クランプ直後は直前値を信頼する」フラグを追加できる。
   `fwd_vopp`・`predict_positions`の両方がこの恩恵を受けられる。
2. **穴④への対応(優先度中)**: 真横通過(`|ds|`が小さい)区間でのマップ除外を、現在の
   単純なenter/exit比較から、「直前周期にincludeされていた車両は、位置予測の信頼度が
   低い間(速度クランプ中等)は除外を保留する」設計に変更する。ただしヒステリシス自体は
   意図された設計(境界チャタリング防止)であるため、変更が別の副作用(除外解除の遅延に
   よるコリドー過敏化)を生まないか慎重な検証が必要。
3. いずれも**AWSIM側のV2X速度推定異常自体(真因)は解決しない対症療法**である点に留意。
   根本原因(なぜd2固有で継続的に発生するか)が不明なままである以上、受信側の防御を
   強化する方針が現実的([[v2x-d2-speed-anomaly-collision-suspected-0803]]のGemini回答
   とも整合)。

## 実装(2026-08-03、PartB-1): 穴②(fwd_vopp=0のclosing過大評価)への対処

`v2x_vehicle_tracker.py`の`V2XVehicleTracker`にクランプ時のフォールバック機構を追加した
(config.yaml `v2x_obstacle_avoidance.clamp_hold_enabled`、**既定false=現行の0クランプを
完全維持**)。

- 有効時、クランプ発生から`clamp_hold_freshness_s`(既定0.5s)以内は直前の有効速度を
  そのまま返す。
- 鮮度切れ後は0(=穴そのもの)には戻さず、直前の進行方向を維持しつつ大きさだけ
  `clamp_fallback_mps`(未指定時はデフォルトで`v_max_safety`自体、物理的に想定しうる
  最大速度)へ差し替える。これにより`closing_est`は常に「相手を実際より遅く見積もる」
  安全側へ倒れる。
- 直前の有効速度が一度も無い車両(起動直後等)はフォールバックしようがないため、
  既存どおり0のまま(退行なし)。

単体テスト5件を追加(既定OFF時の現行挙動不変・鮮度期限内保持・鮮度切れ後フォールバック・
フォールバック値未指定時の既定・直前値皆無時の安全側維持)。回帰スイート全体3001件PASS
(既存2996件+新規5件)。

### dev3での検証手順(提案、未実施)

dev3の実走行ログ(2本、v_max差実験)を確認したところ、**V2Xクランプは0件**だった —
ローカル環境ではこの現象が自然発生しないことが分かった。実地検証には人工的な注入が必要。

1. **オフライン再現(推奨、最も確実)**: 既存の0803-02 rosbag(実際にクランプが発生した
   実データ)を`ros2 bag play`で再生しつつ、`clamp_hold_enabled=true`のmpc_controller
   ノード単体(AWSIM無し)を起動し、`fwd_vopp`/`closing_est`のログ推移がOFF時とどう
   変わるかを比較する。実車両制御に一切影響を与えず、既に発生した異常データをそのまま
   使えるため安全性が高い。
2. **オンライン人工注入(補助的)**: dev3起動中に`ros2 topic pub`で対戦車のV2X
   メッセージへ人工的な位置ジャンプを一時的に注入し、ON/OFFでの挙動差を観察する。
   AWSIM自体のpublishと競合するリスクがあるため、実施の際は慎重に(トピック
   リマップ等の分離を検討)。

有効化の判断(config値をtrueへ変更するか)は、上記いずれかの検証結果を見て人間が行う。
