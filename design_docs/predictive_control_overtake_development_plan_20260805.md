# オーバーテイク判断への予測制御導入 開発計画書(Part C)

**ステータス**: 起草(task#293)。Part A(283節、判断パイプライン監査+V2X予測消費先監査+
予測精度実測+近視眼事例)・Part B(292/296節、シャドー2-QP評価)の結果を踏まえた
実装計画。本書自体はコード変更を伴わない。

## 1. 背景・動機

### 1.1 Part Aで確定した事実(283節)

- V2X等速外挙による真の未来位置予測(`v2x_vehicle_tracker.py`の`predict_positions()`)
  は実装済みで、約0.5秒先まで複数サンプルを生成できる。
- しかし離散判断層(側選択・ENGAGE・giveup)の唯一の入口である`_scan_traffic()`が
  `predict_positions(vid, [0.0])`と**明示的にt=0のみ**を要求しており、V2X予測結果は
  判断層に届く前に現在値へ差し戻されている。
- 予測精度実測: 単純な現在トレンドの外挿は概ね1〜1.5秒先までは実用的な精度(数十cm級)
  を保つが、2秒を超えると誤差が側判断の閾値(along_min_width=1.45m等)に匹敵する規模
  まで拡大する。
- 近視眼事例2件(0804-06ログ): switchback発火の約1〜2秒後にroom_exhaustedで強制giveup
  するパターンを確認。決定時点でコリドーの短期変化を先読みしていれば回避できた可能性。

### 1.2 本日(2026-08-05)得られた追加の裏付け(298節)

- ENGAGE後のgiveup率は**70.1%**(n=388)ときわめて高い。理由の8割超
  (`lat_ttc_C2`+`lat_ttc_FOOTPRINT_RISK`)は295節で「物理下限であり緩和不可」と
  結論した閾値由来であり、そのうち**37.1%が2秒以内、70.2%が5秒以内**に発火している。
  → ENGAGE時点では安全マージンがあったのに、短時間で状況が悪化して失敗するケースが
  支配的であることの定量的な裏付け。
- OT必要最小オフセット計算(`min_needed_mag`)は対象車の**現在**の横位置のみを使って
  おり、対象車が移動中であることを一切考慮していない。ユーザー指摘「相手も走行して
  いるので、次の瞬間にかわそうとしていた相手はもうそこにはいない」はこれを的確に
  言い当てている。

### 1.3 結論: 予測制御が有効に働きうる箇所は複数ある

Part Aの結論(「1〜2秒程度の短いホライズンを、確率的な扱いとともに導入する」)を
維持しつつ、具体的な適用箇所を以下の3つに整理する。

## 2. 適用候補(優先順位付き)

### 候補①: OT必要最小オフセットの速度考慮(最小実装、最優先)

**現状**: `_target_mag`計算(mpc_controller.py、298節続報で一部修正済み)は
対象車の**現在**の横位置`_opp_lat_now`のみを使う。

**改善案**: 対象車の縦方向速度`fwd_vopp`(既存、`_scan_traffic()`で取得済み)と、
自車がその対象車の横を通過するまでの推定所要時間(自車速度・相対距離から算出、
新規計算不要——既存の`_closing_est`/`t_reach`計算を再利用可能)を使い、
「通過する瞬間」の対象車の横位置を予測してから必要最小オフセットを計算する。

ただし横方向の予測(対象車が幅寄せ中か直進中か)は不確実性が高いため、まずは
**対象車が直進(横方向速度ゼロ)と仮定した縦方向のみの予測**(=「通過タイミングの
ズレ」を補正するだけ、横位置自体は現在値を使う)から始めるのが安全側の第一歩。

**リスク**: 低。既存の`min_needed_mag`計算に予測時刻を1つ差し込むだけで、
コリドー計算・状態機械には触れない。

### 候補②: ENGAGE判定への短期先読み(298節の70%giveup率への対処)

**現状**: `_dlat_ttc_veto`(closing trend判定)はENGAGE時点の直近数周期
(min_trend_cycles=3)のトレンドのみを見る。

**改善案**: V2Xの`predict_positions()`を使い、1〜1.5秒先(Part Aの精度実測で
実用的と確認された範囲)の対象車位置を予測し、その時点でも十分な横方向クリアランスが
維持できそうかを、ENGAGE判定の追加項として(既存の`_cheap_ok`/`_plan_ok`とは別の
新規ゲートとして)導入する。

**リスク**: 中。ENGAGE判定はCLAUDE.md §1.3の直接の対象ではないが、148/190節系列で
慎重にチューニングされてきた実績があるため、新規ゲート追加は既存条件を置き換えず
ANDで追加し、config gateでON/OFF切替可能にする。Part Bのシャドー評価と同様、
まず診断ログのみ(判断への反映なし)で1〜2秒予測の的中率を実測してから、実際に
ゲートへ組み込むかを判断する2段階방식を取る。

### 候補③: switchback/room_exhaustedの短期先読み(近視眼事例2件への対処)

**現状**: switchback判定は判定時点(N=20ステップ≈12m先)のコリドー形状のみを見て
おり、その後の数秒での短期的な変化トレンド(corr_boundの時間微分)は見ていない。

**改善案**: 283節の近視眼事例で提案した通り、決定時点でコリドーの短期変化トレンドを
1〜2秒先まで外挙し、新側でも早期にroom_exhausted条件へ抵触しそうかを事前チェックする。

**リスク**: 高。CLAUDE.md §1.3で明記されている「switchback判定への安易なガード追加は
厳禁」(82/83節の教訓)に直接抵触しうる領域。着手する場合は等価性回帰(1.4節)相当の
慎重さで、既存のswitchback成立条件を狭めるのではなく、新側選択の「順位付け」
(複数の新側候補があるとき、より安全な側を優先する)という非破壊的な形での導入を
検討する。

### 候補④: 追い越し地点(コーナー)推定によるオフセットランプの遅延開始(最短距離オーバーテイク)

**背景(2026-08-05追記)**: ユーザー提案「自分の車速と相手の車速を意識した追い越し
アルゴリズムを設計」「できるだけ最短距離でオーバーテイクを遂行する」「相手を
追い越すコーナー(地点)を推定し、そこまでは既定経路(レースライン/コリドー中心)
を走行する」。

**現状**: ENGAGE成立後、オフセットランプ(`_ot_alpha`)は即座に0→1へ漸増を開始する
(`_ot_ramp_time`=0.5秒、または`RAMP-BYPASS`で相手が停止/低速の場合は即座にフル
オフセット)。相手がまだ遠く、実際に横に並ぶまで数秒かかる場合でも、ENGAGEした
瞬間からレースラインを外れ始めており、結果的に必要以上に長い距離・時間を
オフセット状態で走行している。

**既存の活用可能な機構**: `_predicted_time_to_wp(from_wp, to_wp, max_dist)`
——コース既知の区間速度プロファイル(`ref_vel_configulator`、コーナーごとの
計画速度)を弧長積分し、自車が特定waypointへ到達するまでの予測時間を計算する
関数が既に実装されている(3549行目付近)。現在は「相手が停止/低速の場合のみ」
ENGAGE可否判定の`_close_enough`計算に使われており(`_is_stopped_for_profile`
条件)、相手が走行中の場合には使われていない(`_engage_dist_dynamic`のv_pot
一定近似へフォールバック)。

**改善案**:
1. 相手が走行中の場合にも拡張する。相手の現在弧長位置+速度(短時間は一定と
   仮定)と、自車の区間速度プロファイル(既存の`_predicted_time_to_wp`と同じ
   積分)から、「自車が相手に追いつく地点(弧長・waypoint)」——すなわち
   ユーザーの言う「追い越すコーナー」——を予測する。
2. ENGAGE自体は現状の距離閾値のまま行うが、**オフセットランプの開始を、
   予測した追いつき地点の手前(ランプ所要時間分だけ先行)まで遅延させる**。
   ENGAGEしてから実際に追いつくまでの間はオフセット=0のまま既定経路
   (レースライン/コリドー中心)を走行する。
3. これにより、必要最小限の距離・時間だけオフセット状態を維持する
   「最短距離オーバーテイク」を実現する。

**候補①(min_needed_mag速度予測)との関係**: 候補①はオフセットの**大きさ**
(magnitude)を対象車の予測位置に基づいて最小化する(実装済み・300/301節)。
候補④はオフセットの**開始タイミング**(timing)を最適化する。両者は独立した
軸であり、組み合わせることで「必要な分だけ・必要なタイミングだけ」の
オーバーテイクに近づく。

**既存RAMP-BYPASS(155/160節)との関係**: RAMP-BYPASSは「相手が停止/低速
なら、ランプを省略し即座にフルオフセットにする」設計(早期に安全マージンを
確保すべき、というロジック)。候補④は逆に「相手が走行中なら、幅寄せ開始を
遅らせて距離を最小化する」——両者は相手の状態(停止/走行中)で使い分ける、
補完的な設計になる。

**リスク**: 中〜高。オフセットランプ機構(`_ot_alpha`/`_ot_ramp_time`)は
CLAUDE.md §1.3の直接のリストには無いが、155/160/168節等多数のセッションで
慎重に調整されてきた領域。特に「ランプ開始を遅らせる」ことは、予測が外れた
場合に横方向の危険域接近への対応が遅れるリスクがあり、304節で発見した
LAT-TTC反応遅延パターン(危険検知〜衝突が0.2〜0.5秒)と相互作用する可能性が
高い——予測が外れて遅延開始が裏目に出ると、既に反応時間の乏しい安全機構に
さらに負担をかける組み合わせになりかねない。

**推奨実装順序**: ①(診断のみ)相手が走行中の場合の追いつき地点予測ロジックを
まず追加し、ログにのみ出力(制御へは未反映)、実測で予測精度を検証する。
②精度が確認できたら、config gate(既定OFF)でランプ開始タイミング制御へ接続。
③dev3実地でn=2以上の検証を経てから既定ONへ切り替えを検討する。

## 3. 実装順序の提案

1. **候補①**(OT必要最小オフセットの速度考慮)を先に実装・dev3検証する。
   リスクが最も低く、本日のmin_needed_mag凍結修正(298節続報)の自然な延長。
2. **候補②**(ENGAGE先読み)は、まず診断ログのみ(Part Bのシャドー2-QPと同じ
   config-gated・判断へ非反映のパターン)で1〜1.5秒予測の的中率を実測してから、
   実際のゲート化を判断する。
3. **候補③**(switchback短期先読み)は候補①②の結果を見てから、慎重に着手可否を
   再検討する。CLAUDE.md §1.3の対象領域のため、単独では着手しない。
4. **候補④**(追い越し地点推定によるランプ遅延開始)は、候補①(実装済み)の
   自然な拡張として優先度が高いが、既存のオフセットランプ機構(155/160/168節で
   調整済み)に触れるため、まず外部AI相談用のプロンプトを作成し設計を
   ブラッシュアップしてから、診断ログのみの段階的実装に着手する。

## 4. 非対象・保留事項

- フルRobust MPC(相手急減速ワーストケース、CLAUDE.md §3項目16で棄却済み)は対象外。
- 異方性(楕円)反発ポテンシャル場(同項目17で棄却済み)は対象外。
- 予測ホライズンは1〜2秒に限定する(283節の精度実測に基づく、2秒超は誤差が
  判断閾値に匹敵し逆効果のリスクが高い)。
