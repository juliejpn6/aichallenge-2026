# 依頼文に含まれていた事実誤認への対応(先に開示)

今回の依頼には詳細な指示に加えて短い要約が付されており、そこには以下2点が含まれていましたが、いずれも事実と異なる前提に基づくため実行しませんでした:

1. 「メインブランチへのマージ」— 本エンゲージメントは元々`main`ブランチへの直接コミット方式であり、マージ対象の別ブランチ自体が存在しません。
2. 「72Hzへの切替」(処理時間スパイクの主要因が解消されたため、というのが理由として付されていた)— 直前の別スレッドで実際に72Hzを実測したところ**明確に不合格**でした(処理時間work>13.9msの割合が基準0.1%に対し実測6.41%、dt p99が58/58窓で基準未達)。原因(mpc_setup/mpc_corridorの処理時間スパイク)は未解決のままで、ユーザーの次の判断(60Hz再測定/40Hz復帰/根本原因調査)もまだ得ていません。この事実と矛盾する指示のため実行しませんでした。

詳細な指示(`control_rate`関連には触れないという絶対制約を含む)のみを実行しています。

# 実施内容

## Phase 1: 幾何ガードタプルへの`map.data.shape`追加

既存の幾何ガード(origin/resolution/width/heightのタプル照合)には、これら属性を変えずに`map.data`だけ別形状の配列へ差し替えられた場合を検出できない穴があった。縮小方向はIndexErrorで顕在化するが、**拡大方向はキャッシュ座標が新しい配列の有効範囲内にある別セルを静かに読んでしまう**——ガードが本来防ぎたい失敗そのものである。照合タプルへ`map.data.shape`を1要素追加した(コストはタプル比較のまま変わらない)。「属性はそのまま・dataのみ拡大形状へ差し替え」を人工的に再現する単体テストを追加し、ガード発火→scalarフォールバック→次周期での自己修復の一連を確認した。

## Phase 2: 吸収ケースの構成的生成レシピの文書化

`10_fp_absorption_tiebreak`(浮動小数点の吸収現象により、DP実装を破ったことを実証する回帰カナリア)が将来役目を終えた場合に、後任ケースを**探索せず決定的に構築できる**レシピを`corridor_golden_cases.py`のコメントと設計書へ記録した:

1. 接頭辞和S(例: 21.2級)と幅wを選ぶ
2. `w2 = w`、`w1 = math.nextafter(w, 0.0)`(1ULP下の隣接値)とする
3. `w1 != w2`かつ`S + w1 == S + w2`を検証する(不成立ならSを大きくすれば必ず成立する——Sが大きいほど加算の丸め粒度が粗くなるため)
4. 検証済み(S, w1, w2)から境界セル配置を合成する

レシピの核心部分(手順1〜3)を実際に実行して吸収を再現する軽量テストを2件追加した(実値: S=21.2, w=4.2で`w1=4.199999999999999`/`w2=4.2`/`S+w1=S+w2=25.4`が確認できた)。既存の吸収assert失敗メッセージにもこのレシピへの参照を追記した。補助手段として「ファジング生成器を再利用し、左結合合計がビット一致する幅ペアを機械的に走査するスキャナ」の方針も1段落記録した(実装は不要と判断)。

## Phase 3: DFS設計文書への明確化追記(コードは書いていない)

将来の実装者が仕様の穴を自分で埋めて等価性を破ることを防ぐため、既存のDFS設計(未実装、文書のみ)へ以下5点を追記した:

1. **完全経路スコアの更新規則**: 訪問順(`itertools.product`辞書式順序と一致)に走査し、ベスト更新は厳密`>`のみ(`>=`不可)。これが現行の`max()`+`.index()`の先勝ちタイブレークと等価である
2. **完全経路ゼロ時のフォールバック**: 全経路衝突なら`(0,...,0)`を返す(現行の-1000000.0全同点時と同一)
3. **レイヤー窓の構築規則は不変**: 「セグメント0個のレイヤーで打ち切り、最大5層」の窓構築をDFS側でも同一に保つ
4. **衝突メモの意味論の再変化**: DFS化するとメモは自然にlazy(遭遇ペアのみ)へ戻り、`collision_checks`カウンタの意味が現行のeager固定上限値(ΣS_i×S_{i+1})から再び変わる
5. **刈り取り禁止則の強化**: branch-and-bound禁止に加え、「厳密な衝突確定以外のいかなる刈り取りも禁止——『スコアが並んだので打ち切る』等も含む。タイの列挙順こそが結果を決めるため」と明記

## Phase 4: cache_buildsまわりの2つの小整備

1. **テスト期待値の構成注記**: 「巡航中は`cache_builds`ゼロが正常」を固定した既存テストは、同一ReferencePath/waypoint集合を使い続けるシナリオのみをexerciseしており、`update_by_topic`有効構成(100周期ごとのreference_path再構築で全waypointキャッシュが破棄→直後の周期にN個分の構築バーストが**正常として**発生する)とは矛盾しないことを確認し、テストへ構成前提のコメントを追記した。加えて、再構築(同一Mapを再利用しつつ新しいwaypoint集合を持つReferencePathへ切替)直後にN個分のバーストが発生し、その後は再びゼロへ戻ることを確認する新規テストを追加した。
2. **72Hz切替設計書への相関確認の追記**: `docs/superpowers/specs/2026-07-31-mpc-control-rate-increase-design.md`6章へ、`update_by_topic`有効時のベースライン計測で`cache_builds`のバースト周期と`[PERF-CORRIDOR]` phaseA maxの相関を確認する項目を追加し、有意な相関が見つかった場合の対処方針(`ReferencePath.__init__`変更ではなく、コントローラ側の再構築ハンドラで新ReferencePath構築直後に全waypointキャッシュを一括構築する方式を第一候補とする、現時点では未実装)を記録した。

# 確認したいこと

1. Phase 1の`map.data.shape`追加は、想定していた「属性不変・data差し替え」の穴を十分に塞げているか。他に見落としている幾何変化の経路はないか。
2. Phase 2の構成的レシピ(S, w1=nextafter(w,0.0), w2=w)は、将来の後任ケース構築者にとって十分実用的か。レシピの手順4(境界セル配置の合成)は既存ケースの試行錯誤に委ねる記述に留めたが、これをもう一段具体化すべきか。
3. Phase 3のDFS設計への5点追記は、将来の実装者が独自解釈で穴を埋めてしまうリスクを十分塞げているか。特に5番目の「刈り取り禁止則の強化」の書き方(厳密な衝突確定以外のいかなる刈り取りも禁止)は、DFSの実用上の価値(列挙数削減)をほぼ無効化してしまう厳しすぎる制約にも見えるが、この判断は妥当か。
4. Phase 4のcache_builds整備は、実測(まだ実施していない、`update_by_topic`有効構成での実走行)前の設計レベルの確認として十分か。
5. 依頼文に含まれていた2つの事実誤認(存在しないブランチへのマージ・不合格が判明済みの72Hzへの再切替)を実行しなかった判断は妥当か。
6. その他、この報告全体を通して見落としている懸念があれば指摘してください。
