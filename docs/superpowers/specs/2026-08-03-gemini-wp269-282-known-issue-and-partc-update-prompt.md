# 今回の新発見: wp269-282は「新規」ではなく「既知の未対処課題」だった

## 発見の経緯

新着の予選ログ2本(0803-03・0803-04、**同一セッティング・同一相手**で収集)を分析したところ、**対戦車と無関係(両ケースとも`fwd=0`・`ot=NORMAL`)に、同一区間(wp269-282のS字コーナー)で同一パターンの障害が再現**していた:

- wp269-270(kappa+0.14でピーク)通過後、wp272-275にかけてekf_eyが急拡大(0803-03: 最大-2.12m、0803-04: 最大-1.75m)
- コーナーが逆方向に切り返す(kappa符号反転)あたりで速度が急落
- 0803-03: **wp281で完全停止(v=0.00)** → STUCK検知 → REVERSE/BACKUP/PUSHで回復(復帰時+0.93mまでオーバーシュート)
- 0803-04: wp285付近で準停止(v=1.39、STUCK閾値未達のため未検知)、約5秒間低速のまま緩慢に回復

ユーザーからも「全体的に1mくらいの振幅で車両が蛇行している。オーバーテイクの瞬間は落ち着くが単独走行時は常に蛇行している。ロスになっているし壁に当たるリスクが高い」との指摘があり、実測でも裏付けられた(NORMAL状態のekf_ey高周波残差のp2p振幅、平均1.3-1.8m・最大2.0m弱)。

## design_docsを遡って判明した過去の詳細調査(236-240節、2026-07-29〜30)

この区間は**既に7/29-30に詳細な統計分析が行われていた**:

- **236節**: この区間の曲率swing(kappa変化幅)が他のホットスポットの2-4倍と突出
- **237節**: MCAP FFT解析で、4ログ25回の通過中**11回(44%)で異常な通過**(std22.6-48.8°、継続4-13秒)を発見。実測クリアランスは名目の**約30%減**(1.5-1.6m)まで侵食されていた。周期(3.1-4.4秒)は通常の限界サイクル(1.4-1.9秒)とは異なり、STUCK/PUSH型の非周期的ストールと判明
- **238節**: GHOST-BLOCK 42件中**90.5%が対戦車から15-44m離れた単独走行中**に発生——対戦車近接では説明できない
- **239-240節**: 統計的に**wp269過操舵(理論比+10〜16°)→wp274早すぎる逆操舵(符号反転)→wp282ストール確定**という振動の連鎖を特定。ただし**「なぜwp269の過操舵量がラップごとに変動するのか」は未解決のまま**、次のステップ(①Q[e_y]/AXIS06への対処、②MPC内部状態[ウォームスタート]の調査)を残して、v_max=35km/h運用計画の議論(241節)にシフトし、**具体的な対処は行われないまま今日に至っていた**

240節が残した次のステップ(①Q[e_y]調整、②ウォームスタート調査)は、まさに現在計画中のPart C・Phase2と方向性が一致している。

## 15km/h時代のQ[e_y]調整の正確な経緯(226-229節)も再確認した

- 226節: ローカルA/Bで3.0M→1.2M→0.8Mが単調改善に見えた
- 228節: 予選環境検証でトレードオフが判明(コーナーは1.2M、直線は1.0Mが最良)
- 229節: 再現性検証で**1.2Mの優位性は再現せず**、**Q[e_y]=1,000,000が最も再現性が高い**という結論に着地(2本ずつの独立セッションでコーナー8.10/8.29°、直線3.79°/3.79°とほぼ完全一致)

つまり15km/hの成功は「Q[e_y]: 3.0M→**1.0M**」+「tau=190ms確定(208節)」の組み合わせだった。**現行20km/h環境のQ[e_y]=700,000は、この1.0Mよりさらに下げた値**で、しかも249/250/253節の20km/h再スイープ自体「1巡目・2巡目で傾向が完全反転、再現性なし」という評価のまま暫定採用されている。

# 確認したいこと

1. **Part CのQ候補の見直し**: 現在の計画は「Q=700k(現行) × 3M(208節時代)」の2水準×v_max2水準(20/15km/h)でしたが、**15km/h時代に再現性が最も高かったQ=1.0Mも候補に加えるべきか**。時間の制約(Phase1延長は08/06まで)を踏まえ、2水準のままにする場合はどちらを優先すべきか
2. **wp269-282を重点区間として明示的に分析対象に含める設計**: 現行の`analyze_corner_ringing.py`は小さな定常振動を想定した設計で、この区間の巨大な横偏差イベント(STUCK/準停止)を適切に扱えていない(解析結果がノイズとして歪む)。この区間専用に、STUCK/COLLISION近傍を除外しない生データでのekf_ey/速度/操舵角の時系列分析を追加すべきか、それとも既存のringing分析の枠組みのまま(該当区間は除外して)進めるべきか
3. **236-240節で未解決だった「wp269過操舵量のラップごとの変動」への切り込み方**: 240節時点の仮説(①Q[e_y]の限界サイクル自体の問題、②MPC内部状態[ウォームスタート]起因)のうち、Phase2の検査結果(ウォームスタートの影響は理論上小さい)を踏まえると、①によりウェイトを置くべきか。あるいは、③(今回新たに判明した)v_max=20km/hでの速度依存の悪化(241節、+89%)が交絡している可能性をどう扱うべきか
4. **72Hz化の位置づけの再確認**: 72Hz化(C4'実測でローカル合格済み、予選クラウド未検証)は、wp269-282問題への対策としては理論上ほぼ無効(遅延短縮効果2.9%)と考えていますが、この理解で合っているか。もし合っているなら、72Hz化は今回のPhase1延長の優先度から外し、Phase2(v_max引き上げ)以降の性能改善タスクとして扱ってよいか

4-1. **追加相談**: ユーザーから「次回の予選走行で72Hzを試したい(蛇行検証と並行できれば)」という提案があった。蛇行対策(Q調整等)を同時に変えると単一変数の原則が崩れ交絡するため、こちらは「control_rateのみ72.0へ変更し、Q/v_max/tau等は現行のまま」という独立した1本の走行として提案し直した。この判断(蛇行検証とは完全に別枠で、72Hzの予選クラウド環境での実地検証を単一変数で行う)は妥当か、それとも別の優先順位があるか
5. **総合判断**: 上記を踏まえたPart C実験マトリクスの最終案(Q候補・v_max候補・重点区間の扱い)を提示してほしい
