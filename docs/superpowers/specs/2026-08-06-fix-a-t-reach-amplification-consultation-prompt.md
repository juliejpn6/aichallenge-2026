# 背景

`design_docs/opp_lat_pred_overlap_guard_design_20260806.md`の設計(Fix A:
`opp_lat_pred`の速度推定を自前差分からV2Xトラッカーの既存速度推定
[`tracker.velocity()`]の再利用へ置き換える)について、実際のqualifying
ログ(`autoware(0805-07).log`+同名rosbag)のV2X受信列(`/v2x/vehicle_
positions`、実測publish rate≈15.2Hz)を使ってPhase 1のオフライン反実
仮想検証を行った。

## 実施内容

rosbagから対象車(d2)の実際の位置受信列を取り出し(CDRを手動デコード)、
40Hz制御ループがこの15.2Hzデータをどう読むかをシミュレートした上で、

- **旧方式**: 40Hz固定dtでの単純差分(現行実装のミラー)
- **新方式(Fix A)**: `v2x_vehicle_tracker.py`の窓端点差分(既存の
  `speed_window=6`)を横方向へ射影

の両方で速度推定・`opp_lat_pred`・`min_needed`を再構成し比較した。

## 結果1: 速度推定そのものは劇的に改善(明確な成功)

| | 最大値 | 平均 |
|---|---|---|
| 旧方式(40Hz固定dt単純差分) | 26.7 m/s(物理的にあり得ない) | — |
| 旧方式(クランプ+EMA後) | 1.30 m/s | — |
| 新方式(tracker.velocity()窓端点差分) | 7.37 m/s | 5.83 m/s |
| 参考: 1秒間隔の粗い実速度(独立算出) | 6.70 m/s | 5.75 m/s |

新方式は独立参考値にほぼ一致。旧方式は物理的に不可能な値を頻発。

## 結果2: opp_lat_pred/min_neededまで通すと結果が混在(想定外)

12サンプル中8件は改善方向だったが、3件(側=-1)は悪化、うち1件
(`t_reach=1.5秒`、外挿時間の上限)では新方式のmin_neededが**0.000**
(旧方式の2.758より悪化)という逆転が起きた。

**解釈(暫定)**: `opp_lat_pred = opp_lat_now + lat_vel * t_reach`という
外挿式は、速度推定`lat_vel`がどれだけ滑らかになっても、`t_reach`
(最大1.5秒)を掛けることで**残存するわずかなノイズ・実際の速度変動を
増幅する**性質を本質的に持つ。Fix Aは入力(速度推定)のノイズを大幅に
減らすが、外挿という演算自体の脆さは解消しない。

## 検証手法の限界(正直な開示)

このPhase 1検証は簡易なオフラインミラー実装であり、以下の近似を含む:
(a) `_closest_wp_and_s`のprev_idx半径制限を省略しグローバル探索を使用、
(b) `clear_needed`(モデル幅+ブロック半幅)を実測ログから中央値として
逆算した近似値、(c) `t_reach`は実測ログの値をそのまま再利用(自前で
再計算していない)。実装・単体テストによる確定検証はこれから行う。

## 相談したいこと

1. **この「t_reach外挎によるノイズ増幅」という現象は想定内でしたか?**
   design書のFix Bの位置づけ(コリドー実測を優先する物理的な床、速度
   予測の不確実性に依存しない安全網)は、この結果によってさらに正当化
   されたと考えていますが、この理解で合っていますか?
2. **Fix A自体に、t_reach起因の増幅を緩和する改善を追加すべきでしょうか?**
   候補:
   a. 速度推定へさらに軽いスムージングを追加する(ただし追加の遅延・
      新規パラメータを増やすリスクとのトレードオフ)。
   b. `t_reach`自体の上限(現行1.5秒)を状況に応じて動的に短縮する
      (ただし別の目的[近視眼防止]で導入された値であり、安易に触ると
      別の退行を招くリスクがある——14節参照)。
   c. 何もしない(Fix Bが安全網として機能する前提のまま、Fix Aは
      「入力ノイズの除去」という当初の狭いスコープのまま実装する)。
3. wp85(t_reach=1.5秒での逆転)は、私の簡易ミラー実装のバグ・近似の
   誤差である可能性はどの程度あると思いますか? 実装後の単体テストで
   優先的に再現・検証すべき具体的なケースとして扱ってよいでしょうか?
4. この結果を踏まえても、§10の段階導入計画(Fix A→B→Cの順、まずFix A
   単体をdev3・予選環境で検証してからFix Bへ進む)は変更不要と考えて
   良いでしょうか、それとも計画自体を見直すべき示唆がありますか?

以上、率直な意見をお願いします。
