# 背景

本日終日調査していた`opp_lat_pred`(オーバーテイク中、対象車の横方向速度を
自前でEMA推定し、通過予測時刻まで外挿して必要最小オフセット`min_needed`を
計算する機構、候補①、既に本番投入済み)のクランプ張り付き問題
(`2026-08-05-opp-lat-pred-clamp-saturation-consultation-prompt.md`で
一度相談済み)について、**実際の衝突を引き起こした具体的な1事例**が
見つかりました。

## 実装(再掲)

```python
lat = math.cos(wp.psi) * (cy - wp.y) - math.sin(wp.psi) * (cx - wp.x)
# ↑ 対象車位置を、対象車自身の最近傍waypointの方位角基準の局所座標系へ変換

if (self._ot_opp_lat_prev is not None
        and self._ot_opp_lat_prev_vid == self._ot_target_vid):
    dt = 1.0 / control_rate  # 40Hz
    raw_lat_vel = (opp_lat_now - self._ot_opp_lat_prev) / dt
    raw_lat_vel = clamp(raw_lat_vel, -2.0, 2.0)
    opp_lat_vel_ema += 0.05 * (raw_lat_vel - opp_lat_vel_ema)
opp_lat_pred = opp_lat_now + opp_lat_vel_ema * t_reach  # t_reach最大1.5秒

min_needed = f(opp_lat_pred, 相手車幅, 安全マージン)  # 必要最小オフセット
offset = g(min_needed, corr_bound(コリドー実測))       # 実際の指令offset
```

## 衝突事例(dev3、3台自己対戦、wp215→233)

自車がside=1(左)でOVERTAKING中、対象車とほぼ同じwaypoint帯
(wp232-237付近)に同時に存在し、速度が4.53→1.22m/sへ急落(衝突)しました。

| wp | offset(指令) | min_needed(必要量) | 達成率 | opp_raw_lat_vel(クランプ前生値) |
|---|---|---|---|---|
| 215 | 1.05m | 3.00m | 35% | 0.73 |
| 221 | 0.82m(**減少**) | 3.00m | 27% | 0.09 |
| 227 | 1.43m(増加) | 2.29m | 62% | **3.691**(クランプ上限2.0を超過) |
| 233(衝突直前) | **0.07m**(崩壊) | 2.29m | 3% | 1.399 |

**重要**: コリドー自体(選択した左側)は`ub0=2.69〜5.30m`と終始十分な空きが
ありました(wp221/227では5m超)。**スペース不足が直接原因ではありません**。
にもかかわらず指令offsetは単調に伸びず、上下に振動(1.05→0.82→1.43→0.07)
した末に衝突直前に崩壊しました。この振動は、wp227時点で`opp_wp`(対象車の
最近傍waypointインデックス)が230→238(Δ+8)へジャンプし、同時に
`opp_raw_lat_vel`が3.691という異常値(クランプ上限2.0を明確に超える生値)
を記録したタイミングと完全に一致しています。`opp_lat_pred`(EMA後の値)も
1.783→0.244へ1ステップで約8割急落しました。

**注意**: n=1の1事例であり、この3.691という値が「相手も回避行動中で
実際にそれだけ速く動いた」可能性を完全には排除できていません(対象車が
本当にそれだけの横方向速度を出しうるかは未検証)。

## 対策候補(初期評価つき、優先度は暫定)

**①生値クランプの物理的妥当性強化**: 現行±2.0m/sを、相手車の実際の
運動性能(横加速度限界)から導いたより厳密な範囲へ絞る。ただし今回の
3.691が正当な動きだった場合、締めすぎると本当に必要な急旋回まで潰す
リスクがある。

**②コリドー実測を優先し、min_needed/offsetの下限をコリドー実測値で
保証する(現時点の本命候補)**: 「コリドーに十分な空き(例: 5m超)がある
場合は、`opp_lat_pred`の変動に関わらずoffsetの下限を保証する」という
ガードを追加する。空間認識(corr_bound、安定して計算できている)を優先し、
相手速度予測(opp_lat_pred、不安定)への依存度を下げる方向。

**③offsetのレート制限に非対称ヒステリシス(下降を緩やかに)を導入**:
`opp_lat_pred`が急落してもoffsetが一気に崩壊しないよう、上昇より下降を
遅くする非対称スムージングを入れる(既存の`r_delta_swing`調査で別AIが
提案した「非対称EMA」と同じ発想をoffset側に適用)。

**④`worth=0`転落時の即時giveup明確化**: wp227で`worth=0`(攻める価値
なし判定)になった後もside=1のまま中途半端なoffsetを出し続けたこと
自体が危険だった。「worth=0になったら即座に安全側(offset維持または
明確なgiveup)へ倒す」という状態遷移の明確化。
