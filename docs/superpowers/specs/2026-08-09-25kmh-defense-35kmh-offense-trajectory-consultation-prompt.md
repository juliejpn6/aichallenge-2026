# 相談プロンプト: 25km/hディフェンス経路・35km/hオフェンス経路の設計方針相談(2026-08-09)

以下をそのまま外部AI(Gemini/Claude等)へ入力してください。

---

## 背景

自作レーシングカートのMPC(Model Predictive Control、空間再定式化された自転車モデル、
OSQPソルバ、制御周期40Hz、`multi_purpose_mpc_ros`)を開発しています。競技ルール上、
**1位走行中は車速が25km/hに制限される**ことが判明しました。そのため、これまでの
「単一の車速目標でパラメータを詰める」方針から、**用途別に2種類のトラジェクトリ
(走行経路)を用意する方針**へ転換しました:

- **25km/hディフェンス経路**: 1位走行時(強制25km/h上限)専用。ゆるいコーナーで
  インに実車幅0.7台分(約1.02m)のギャップを残し、追い抜かれにくくする
  ブロッキングラインを狙う。タイトなコーナー(後述)は可能な限り曲率を緩和し、
  25km/hに近づける。
- **35km/hオフェンス経路**: 先行車に追いつき、追い越しの機会を伺う用(1位以外)。
  純粋に最速ラップを狙う。

**現在の到達状況**: 参照経路CSV(`s_m,x_m,y_m,psi_rad,kappa_radpm,vx_mps,ax_mps2`、
TUM `global_racetrajectory_optimization`形式)の実装を調査したところ、**実行時に
実際に使われるのは`x_m`,`y_m`列のみ**と判明しました(`psi_rad`/`kappa_radpm`は
`utils.load_ref_path()`が返すが呼び出し側で即座に破棄、`ReferencePath`クラスが
x,yのみから独自にリサンプリング・平滑化・kappa再計算・速度プロファイル計算を行う)。
既存の`traj_mincurv.csv`のx,yジオメトリをそのまま流用する「オフェンス版」ファイル
生成は完了・安全確認済みです。

## 本題: ディフェンス経路生成で3連続の失敗

**タイトコーナー2箇所**(`traj_mincurv.csv`のkappa列から特定、いずれもay_max=12.0
[m/s^2]でも理論上25km/h未達):

| 区間(wp_id、1m間隔のCSV行index) | 最大\|kappa\| | 半径R | ay_max=12でのv_cap |
|---|---|---|---|
| wp224-230 | 0.3895 | 2.57m | 20.0 km/h |
| wp247-257 | 0.3423 | 2.92m | 21.3 km/h |

実測トラック幅(TUM形式`w_tr_right_m`/`w_tr_left_m`、`global_racetrajectory_optimization/
inputs/tracks/aic_2024.csv`、座標系が本トラックと一致することを確認済み)では、
この2箇所とも**現在の線が使っている幅より広い余地がある**ことを確認済み(wp224で
片側3.88m/計7.76m、wp247で片側2.96m/計5.92m、対して現状線は明らかにそれより
狭い半径で通過)。

**試したこと(いずれも不採用)**:

1. **タイトコーナーの拡幅**: 区間を移動平均(window 3〜15点)で平滑化し、taper
   (raised-cosine)で原線へ滑らかにブレンド。→ **taper境界付近でピーク曲率が
   むしろ悪化**(wp224の頂点\|kappa\|=0.20が隣接wp225-228で0.24-0.26まで悪化)。
   離散座標への単純box-filterは曲率単調減少を保証せず、ピークをずらすだけで
   悪化させることがあると判明。不採用。

2. **ゆるいコーナー17区間へのイン側1.02mバイアス(1回目)**: 各区間を
   `lo-4`〜`hi+4`のtaper窓でraised-cosine重み付けオフセット。→ 隣接する
   タイトコーナーのcore範囲(保護対象のつもりだった)へtaperが滲み出し、
   保護できていなかった。

3. **同(2回目、保護範囲クリップ追加)**: taper窓をタイトコーナーcore境界で
   単純クリップ。→ **クリップ位置の重みが1.0のまま隣接未処理点(重み0)へ
   直結し、1.02m級の不連続ジャンプが発生**。かえって曲率が悪化。

4. **同(3回目、保護点への距離ベース追加減衰)**: 保護点からの距離に応じて
   重みへ`0.5-0.5*cos(pi*d/taper)`の追加減衰を掛ける方式に変更。→ **保護区間
   自体は変位0を達成できたが、保護区間の外側shoulder領域(wp210-223・231-240・
   243-246・258-262等)で最大0.78 rad/mの新たな曲率悪化が発生**。2つのcosine
   taperの重ね合わせ・法線方向の回転(コーナーなので法線自体も曲がっている)の
   相互作用が原因と推定。

3回とも「生の(x,y)座標へ離散的なraised-cosineオフセットを直接適用する」
アプローチ自体が、この用途(タイトなコーナーのすぐ隣で横オフセットを立ち上げる)
には根本的に脆弱と判断し、この方式でのディフェンス経路生成は一旦中断しています。

## 参考: 競合チームの実測データ(重要な手がかり)

予選環境で観測した競合チーム「未来機械工房」のログ(`autoware.log`)と
rosbag(`/localization/kinematic_state`等)を解析しました。**参照経路CSVは
私たちと完全に同一の`env/final_ver3/traj_mincurv.csv`**でした(パスも一致)。
つまり**経路ファイル自体は同じ**で、蛇行対策込みのMPCチューニングだけで
ラップタイム39.5〜40.3秒(私たちは20km/h運用中心)を実現しています。

彼らのconfig.yaml(ログから復元、抜粋):

| パラメータ | 未来機械工房 | 我々(現行) |
|---|---|---|
| `v_max` | 35.0 | 25.0(暫定確定) |
| `ay_max` | **20.0** | 7.0(12.0へ変更検討中) |
| `delta_max_deg` | **32.0**(我々より小さい) | 52.0 |
| `steer_rate_max` | 1.00 | 1.1 |
| `R`(=[v,delta]) | `[100000, 0.0]`(**R[delta]=0**) | `[100000, 500]` |
| `Q` | `[1.2M, 100M, 1.7M]`(3要素、delta_actual拡張なし) | `[400000, 8000000, 200000, 0.0]`(4要素) |
| `QN` | `[1M, 1M, 1e4]` | `[1M, 1000, 1e4, 0.0]` |
| `steer_low_pass_gain` | **1.0**(フィルタ無効) | 0.6 |
| `accel_low_pass_gain` | **1.0**(フィルタ無効) | 0.35 |
| `wp_id_offset` | 2 | 1 |
| `use_max_kappa_pred` | **true** | false |
| `smoothing_distance` | 2 | 1 |
| `steering_tire_angle_gain_var` | 1.50 | 1.639 |
| `ey_ref_bias`(横目標の置き所) | **1.00(=回廊の中心)** | `line_follow_w`相当0.5(中間) |

**実際の走行ログ(rosbagから復元)で驚いた点**: 私たちの計算ではay_max=12でも
wp224(半径2.57m)は理論上20.0km/hが上限のはずですが、**未来機械工房は同じ
wp224付近を実測33.5km/h(v²/R換算で約33.7 m/s²相当のay!)で通過**しています。
一方で参照centerlineからの実測横偏差(signed e_y)はwp224で平均+0.15m、
最大+0.86m程度と、劇的にラインを外側へ膨らませているわけではありません
(数十cm〜1m程度のオフセット)。

推測: 彼らの`ey_ref_bias=1.0`(レースラインでなく「回廊の中心」を追従目標にする
設定、我々の`line_follow_w=0.0`側に相当)+ `R[delta]=0`(操舵コスト無し)+
`use_max_kappa_pred=true`+フィルタ無効という組み合わせが、タイトコーナーの
鋭い頂点そのものを厳密に追わず、コリドー全体を使った**より緩やかな実効曲率の
軌道を自然に選ばせている**のではないか、と考えています(未検証の仮説)。

## お願いしたいこと

1. **タイトコーナー2箇所の曲率緩和(オフェンス・ディフェンス共通で有用)**:
   離散座標への直接編集ではなく、より頑健な幾何アプローチを提案してください
   (例: 3次スプライン/クロソイドベースのC2連続なローカル再パラメータ化、
   実際のトラック幅制約下での局所円弧フィット、等)。あるいは
   `~/global_racetrajectory_optimization`(TUM製、mincurv/mincurv_iqp/mintime対応、
   本トラック用の`aic_2024.csv`・`ggv.csv`[現在ay_max=12.0均一]・
   `ax_max_machines.csv`が既に設定済み)を再実行する場合の、具体的な
   パラメータ変更案(track widthのlocal override、curvlim等)も歓迎します。

2. **ディフェンス用イン側バイアス(17区間、方向[L/R]既知)の、曲率を悪化させない
   実装方式**: 上記3回の失敗を踏まえ、生座標への直接オフセットではない設計
   (例: 目標横偏差を「コスト関数側」で持たせる[Q[e_y]の参照値バイアス]、
   `line_follow_w`/`ey_ref_bias`のセクション別スケジューリング、コリドー
   境界そのものを非対称に狭める、等)を含め、複数の設計案を比較してください。

3. **未来機械工房の`ey_ref_bias=1.0`(コリドー中心追従)アプローチが、我々の
   タイトコーナー速度不足(20-21km/h理論値)を、経路ジオメトリを変えずに
   解消しうるか**、直感的な評価をお願いします。もし有望なら、25km/hディフェンス・
   35km/hオフェンス双方でこの方向性(`line_follow_w`を0側へ、あるいは
   区間限定でスケジューリング)を先に試す価値があるか、意見をください。

4. 上記1-3を踏まえた、**総合的な実装優先順位**(どれから着手すべきか)を
   提案してください。

## 制約・注意事項

- `traj_mincurv.csv`は既存のまま変更しない(新規2ファイルとして出力する方針)。
- 安全マージン: トラック境界から最低1.2m(コリドーの`bicycle_model.width=2.30`
  [+safety margin込み]の半分1.15mよりやや広め)を必ず確保。
- コリドー計算(`update_path_constraints`)自体、および`_corr_bound_ahead`・
  switchback判定等の安全判定ロジックへの変更は、このプロジェクトのCLAUDE.mdで
  「等価性回帰必須・安易な変更禁止」と定められている領域です。今回の相談は
  参照経路ジオメトリ(x,y)の生成、または`line_follow_w`等の既存公開パラメータの
  範囲内での提案に留めてください。
- 締切: 内部締切2026-08-25(以降はレーティング維持優先へ切替)、競技終了
  2026-08-31。
