## はじめに

自律走行レーシングカートの開発で、スタック(壁際で動けなくなる)からの復帰処理として「バックギアに入れて後退する」機能を実装していた。ところが**ローカルのシミュレータ環境(AWSIM)上では、この自動復帰が何日試してもほぼ100%失敗する**という現象に悩まされ続けた。

最終的にはAWSIMの内部挙動を推測しながらの地道な切り分けと、複数のAIとの壁打ちの末に解決したのだが、その過程で「一見合理的に見えた仮説が実は逆効果だった」という展開があり、デバッグの教訓として書き残しておきたい。

## 環境

- ROS2 Humble + Autoware(自作の制御ノードでMPC制御)
- AWSIM(Unity製、TIER4提供のクローズドソースシミュレータバイナリ)
- ギア制御は `autoware_auto_vehicle_msgs/msg/GearCommand`(要求)・`GearReport`(実際の状態)を使うAutoware標準インターフェース

## 症状

スタック検知後、以下の手順でバックギアへ入れようとしていた。

1. `GearCommand.REVERSE` (=20) をパブリッシュ
2. `GearReport` が `REVERSE` になるのを確認して後退開始

ところがローカル環境では、**何百回試してもほぼ確認できない**。`GearReport` はずっと `PARK` (=22) を返し続け、後退も一切発生しなかった。

一方で不思議なことに、AWSIM画面の「Autonomous / Manual」切り替えボタンで手動操作に切り替え、キーボードでギアをRに入れると**一発で成功する**。シミュレータ自体は後退できるのに、ROS経由の自動化パイプラインだけが機能しない ―― この非対称性が最大の手がかりであり、同時に最大の罠でもあった。

## 第一の発見: 送っていた値が仕様外だった

「DからRへ直接シフトできない、必ず中間ギアを経由する」という既存の知見があったため、スタック復帰は D → (中間ギア) → R という手順を踏んでいた。この中間ギアに、自動車の一般常識から**PARK**を選んでいた。

ところが後になって、公式インターフェース仕様を確認したところ、`GearCommand` の `command` フィールドとして明記されているのは

```
1 = NEUTRAL
2 = DRIVE
20 = REVERSE
```

の3値のみで、**PARK(22)は仕様に存在しなかった**。

中間ギアをNEUTRALへ修正したところ、NEUTRALへの遷移確認は成功率0%近辺から**100%**まで劇的に改善した。しかし主役であるREVERSEへの遷移は、相変わらず一切成功しなかった。半分だけ前進、という状態である。

## 第二の発見(そして間違い): 「動き続けなければ拒否される」仮説

ここで複数のAIに状況を相談したところ、有力な仮説が返ってきた。

> シフト受理後も運動指令(速度・加速度)が継続しないと、AWSIM側が「静止+無入力」とみなして自動的にPARKへ戻しているのではないか。手動操作は「Rに入れて即アクセル」の連続動作であり、確認待ちの空白がないこととも整合する。

これは筋が通っているように思えた。実装では、REVERSEの確認を待つ間、速度指令をゼロに保持していたからだ。そこで「確認を待たずに、REVERSE要求と同時に後退運動指令を送り続ける」方式へ変更した。

結果: **状況は変わらなかった**。それどころか、5秒間ずっと後退指令を送り続けても、実速度は完全にゼロ(ノイズレベル)のままだった。

一見もっともらしい仮説が、実測データに裏切られる。デバッグではよくあることだが、ここで安易にさらに別のパラメータ調整(待ち時間をもっと延ばす、送信頻度を変える等)に走らなかったことが、後で効いてくる。

## 転機: 本線コードを完全に排除した最小再現

行き詰まったところで、改めて別のAIから重要な指摘を受けた。

> 直前の観測(t=0でREVERSEが一瞬受理されたように見える)は、その前に手動操作でRに入れていた状態が残っていただけかもしれない。ROS要求が本当に受理された証拠にはならない。

これはまさにその通りだった。自分たちの本線コントローラを完全に停止し、それとは無関係な最小限のスクリプトから、初期状態を明確にした上で改めて試すことにした。

```python
# 初期状態: DRIVE であることを確認してから開始

# 1. NEUTRALへ、加速度は完全ゼロで要求
gc = GearCommand(); gc.command = GearCommand.NEUTRAL
cmd = AckermannControlCommand()
cmd.longitudinal.speed = 0.0
cmd.longitudinal.acceleration = 0.0
# ...確認まで送り続ける

# 2. Nのまま1秒保持(加速度ゼロのまま)

# 3. REVERSEへ、加速度は依然ゼロのまま要求
gc.command = GearCommand.REVERSE
# ...確認まで送り続ける
```

結果は次の通りだった。

```
t=0.08s  NEUTRAL 確認
(1秒保持)
t=0.5s   REVERSE 確認 ← 成功!
t=1.0s〜5.0s  REVERSEのまま安定して維持
```

**確認できた。しかも5秒間、一度もPARKへ戻らなかった。**

この後、REVERSE確定後に負の加速度(後退駆動相当)を送っても、ギアはREVERSEのまま維持された。つまり「動き続けなければ拒否される」という第二の仮説は、**完全に逆だった**ということになる。

## 真の原因: 実車のインターロックに近い挙動

2つの試験結果を並べると、違いは一点だけだった。

| | ギア遷移要求 | 運動指令 | 結果 |
|---|---|---|---|
| 失敗パターン | REVERSE要求と同時 | 同時に非ゼロを送信 | 1秒以内にPARKへ強制リセット |
| 成功パターン | REVERSEを単独で要求 | 確認が取れるまで完全ゼロ | 安定して維持 |

つまりAWSIMは、**「ギア遷移が確定する前に運動指令(速度・加速度)が入っている」ことを、暗黙の拒否条件として扱っていた**。実車のオートマ車で「ブレーキを踏んでいないとシフトレバーを動かせない」インターロックに近い挙動である。

これに気づいた瞬間、すべての観測が一本の線でつながった。

- ローカルで一度だけ偶然成功した事例があった。よく見ると、複数回のリトライを経て、たまたま前のサイクルの遅延応答が「タイミングよく」ゼロ入力の瞬間に間に合っただけだった。
- 手動操作で一発成功するのは、シフト操作とアクセル操作が完全に独立した別のUI入力であり、シフトの瞬間には(たとえ直後にアクセルを踏むとしても)運動指令が競合しないからだった。

## 修正内容

スタック復帰の状態機械を、以下のように変更した。

- REVERSE要求後、`GearReport` が確認できるまでは、**速度・加速度とも完全ゼロ**を維持する
- 確認が取れて初めて、後退のための実際の速度・加速度指令を送り始める

コード変更としては数行の修正だが、たどり着くまでに何度も「もっともらしいが的外れな仮説」を試すことになった。

## 検証結果

3台の自己対戦環境で実測したところ、修正前は**確認成功率がほぼ0%**だったのに対し、修正後は**19回中19回、全て成功**した。実際に後退距離が伸びていく様子(速度が -0.07 → -0.29 → -0.51 → -0.74 m/s と加速していく様子)もログで確認できた。

## 教訓

1. **「もっともらしい仮説」は実測前提で扱う。** 「運動指令を送り続けるべき」という仮説は理屈としては筋が通っていたが、実際には逆効果だった。仮説を実装する前に、最小構成で単独検証する価値は非常に高い。
2. **観測結果の「初期条件」を疑う。** 直前の手動操作の残存状態を、自分の変更の効果と誤認しかけた。時系列の前後関係を丁寧に確認しないと、因果関係を取り違える。
3. **本線コードを削ぎ落とした最小再現は、遠回りに見えて一番の近道になることがある。** 複雑な状態機械の中でパラメータ調整を繰り返すより、無関係な要因を物理的に排除したほうが、結果的に早く核心へたどり着けた。
4. **公式仕様書は最初に確認する。** 中間ギアにPARKを使っていたバグは、仕様書の3行を読めば即座に気づけたはずだった。「一般的にはこうだろう」という思い込みで実装した箇所は、後から仕様と突き合わせる価値がある。

シミュレータ・実車を問わず、「手動では動くのに自動化すると動かない」という現象に遭遇したときは、両者の入力の性質の違い(特にタイミング・排他性)を疑ってみるとよいかもしれない。
