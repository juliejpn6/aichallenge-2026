# 前提(再検討不要、確定済みの事実)

## 計画自体の評価
統一機構仮説(SWING区間で必要な操舵レート dδ/dt ≈ L_wb·κ'·v が実舵レート上限r_maxで飽和し過渡オーバーシュートを生む)は、曲率SWING相関(176節、r=0.81)とv_max支配(Part C)の両方を単一の物理現象として説明できる筋の良い仮説であり、Phase 1を「分析のみ・機構を否定したら停止」というゲート付きにした設計判断も適切と判断した。Gemini相談でも「入力側の急峻さが本質」という同じ方向性の見解が得られている。以下は、この計画をそのまま実装する前に必ず反映すべき修正・追加検証項目。

## コード検証で判明した修正必須事項(3点)

**① κ'(swing)の定義が計画書とコードでズレている**: 計画は「176節のswing定義を再利用」としているが、実際に稼働中のコード(`mpc_controller.py` 7119-7134行目、R[delta] swingスケジュール)は前方16waypoint窓内の`max(kappa)-min(kappa)`(振れ幅)であり、真の空間微分κ'=dκ/ds(単位[1/m²])ではない。Phase 2の式`v_cap(s)=margin×r_max/(L_wb×|κ'(s)|)`は物理的に正しい速度キャップを出すためにdκ/dsが必要で、窓内max-minをそのまま代入すると次元・スケールが合わない(窓の弧長で割っていないぶん過大/過小評価になる)。Phase 1・2ともに、waypoint間の実際の弧長で差分を取る真のκ'計算を新設する必要がある。

**② 「R[delta] swingスケジュールは無罪放免(177節)」という前提の確度が過大**: 実際のmemory(177/178節)を確認したところ、これはCPU予算がほぼ100%張り付いたdev3 3台自己対戦環境(超過率30-45%常態化)での処理落ち原因切り分けテストであり、Part Cのようなクリーンな単体A/Bではない。「boost=0でも改善しなかった」のは事実だが、dev3環境自体の処理落ちと交絡した条件下での結果であり、「元々の蛇行(対戦車なし、v_max=20)にR[delta]スケジュールが効かない」ことの直接証拠ではない。この機構自体は現在もconfig上有効(`r_delta_swing_boost: 400.0`)で削除されていないため、計画書の「無罪放免」という断定は一段確度を下げて扱うこと。

**③ steer_rate_maxの内部実装に関する注意**: `config.yaml`の`steer_rate_max: 1.1`(rad/s raw、コメントに実測109°/sへの較正値と明記)は、`MPC.py`内部では`max_steering_rate`として**κ(曲率)のレート制約**(u[1]、tan(δ)/L相当)に使われており、δ(操舵角)への直接のレート制約ではない。Phase 1で「指令の時間微分」をr_maxと比較する際は、`mpc_controller.py`が使っている`steering_tire_angle_gain_var`(1.639)等の既存換算を通して、ログの指令値と物理的な109°/sが同じ土俵で比較できるよう単位を揃えること。

## Geminiが提起したが計画に未反映の論点

Gemini相談では①曲率参照平滑化(最優先)③Q[e_psi] swingスケジュール(次点)②ノッチ/ローパス(棄却)に加え、**④予測ホライズン(空間長/時間)がv_max=20に対して短すぎるのではないか**という4つ目の切り口が出ている。現計画のPhase 1-3はこれに触れていない。折り込むか、意図的に見送るか判断してほしい。

## 過去調査との照合で見つかった、計画の射程外にある重要な未解決事項

`design_docs/stage15_perf_20260707.html`(Stage1.5、制御欠落=CPU予算超過の調査)とその後続の2つのmemoryを照合した結果:

1. **Stage1.5(CPU/処理落ち)は蛇行の原因として既に明示的に否定済み**(180節、2026-07-25の実予選ログ): 実環境の制御ループ超過率はわずか1.5%(健全)だったにもかかわらず、蛇行はローカルのどの重負荷テストよりも悪化していた(実測std 18.3° vs ローカル最良8.0-8.6°)。したがってPhase 1にStage1.5系の制御欠落チェックを追加で組み込む必要はない——この筋は既に別の実データで棄却済み。

2. **しかし180節はもう一つ、現計画が説明できていない重要な発見をしている**: 実環境の蛇行は**トラック全体で一様に悪化**しており、シケイン(高swing区間)に限局していなかった(直線でも同水準に悪化)。当時は「実際の対戦車インタラクション」が疑われたが、後続の263節(2026-08-02、PSD周波数分析)がこの仮説を検証したところ、OT状態(対戦車対応中)の限界サイクル帯パワーはNORMAL状態より**低い**(0.10-0.78倍)と判明し、この筋は退けられ、焦点が「AXIS06本体(NORMAL時の限界サイクルそのもの)」へ戻された。現計画(rate saturation)はこの「AXIS06本体」の系譜に位置づけられる点で方向性は正しい。

3. **核心的な懸念**: rate-saturation仮説(dδ/dt≈L_wb·κ'·v が r_max で飽和)は**曲率swing駆動**の機構であり、直線区間(κ'≈0)では要求レートがほぼゼロになるため、理論上は直線での蛇行悪化を説明できない。しかし180節の実測(最も信頼度の高い単一の実環境データ)は「直線でも同水準に悪化」という、この仮説と正面から矛盾しかねない結果を示している。現計画のPhase 1は「SWING区間」「wp269-282」という高swing区間だけで層別する設計であり、このままではrate-saturation仮説が直線区間の蛇行を説明できるかどうかを検証しないまま、部分的な成功(コーナーでは相関あり)だけでPhase 2/3へ進んでしまうリスクがある。

# 確認したいこと

1. ①②③(κ'の真の定義への修正、R[delta]無罪放免の確度の下方修正、steer_rate_maxの単位整合)を計画にどう反映すべきか、具体的な修正案を示してほしい。
2. Geminiの④(予測ホライズンの速度依存化)を今回のPhase 1-3に折り込むべきか、それとも別スレッドとして切り出すべきか。
3. **最重要**: Phase 1の分析範囲を、現在の「SWING区間/wp269-282」限定から**トラック全体(特に直線区間、κ'≈0の区間)**へ拡張し、直線でも飽和率・蛇行指標(初期振幅・std等)が高いままかどうかを明示的に検証する設計に修正してほしい。具体的な追加分析ステップの案を示してほしい。
4. もしPhase 1拡張の結果、直線区間でも蛇行が高水準のまま(rate-saturationでは説明できない)だった場合、Phase 1のゲート判定(機構支持/不支持)をどう扱うべきか。「コーナー成分は支持されたが直線成分は別要因」という部分的成立をどう扱い、その場合Phase 2/3(速度キャップ・パス補正)にどこまで進めるべきか、判断の枠組みを示してほしい。
5. 直線区間の蛇行(仮にrate-saturationで説明できない場合)に対する次の調査候補は何か。263節が示唆した「AXIS06本体(NORMAL時の限界サイクル、Q[e_y]とtauの相互作用)」という、curvatureに依存しない自己励起的な機構の可能性を、rate-saturation調査と並行して調査すべきか。
