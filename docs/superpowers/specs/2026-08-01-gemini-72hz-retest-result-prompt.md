あなたは自動運転レーシングカート(ROS2 Humble / Autoware、spatial MPCで制御)のソフトウェアアーキテクトです。以前あなたに報告した72Hz実測不合格(処理時間work>13.9msが6.41%、dt p99が58/58窓で基準未達)を受け、スパイク法医学計装(`[PERF-SPIKE]`)を実装した上で、ユーザーから「パソコンの出力制限がかかっていた可能性がある、現在は解除している」との情報提供を受けて72Hzを再実測しました。結果は**大幅改善したが依然として不合格**でした。次にどうすべきか助言をください。

# 前提(再検討不要、確定済みの経緯)

- 前回不合格の原因調査(Phase 1-4)で、以下を構造的に確定済み: `update_by_topic: false`(reference_path再構築バーストは原理的に発生しない)、コリドー等価最適化は72Hzテストのビルドに搭載済み(Docker実ビルドで`_fs_line_cache`の存在を直接確認)、`[PERF]`の`>25ms`表示ラベルは表示のみのバグで実カウンタ値は常に正しい`>13.9ms`基準を使用していた(修正済み)
- 40Hzでは、スパイク検出閾値を予算の1.2倍(30ms)まで緩めても10分間で一度もスパイクが再現しなかった(`[PERF-SPIKE]`計装で確認)
- `[PERF-SPIKE]`計装: `work > 予算×factor`(既定2.0)の周期を1行ダンプし、周期番号・mod100・区間別実測値・`cache_builds`前サイクル差分(仮説a)・`ru_nivcsw`前サイクル差分(仮説b)・GC世代2フラグ(仮説c)・コリドーセグメント数変化(仮説d)を含める。差分追跡は毎サイクル無条件に更新(発火有無に関わらず)、文字列整形・printのみ発火時に限定(オーバーヘッド規律)

# 今回実施したこと

ユーザーからの情報提供を受け、`control_rate`を再度72.0へ変更し、`[PERF-SPIKE]`計装を持った状態で単一車両シナリオ(`make dev`)を約9分間再実測した。

# [PERF-SPIKE]による帰属分析(実発火33件、約9分間)

- **仮説(a)reference_path再構築**: 33件全てで`cache_builds_diff=0` → **完全に排除**(`update_by_topic: false`と整合、構造的に発生しえない)
- **仮説(c)GC世代2**: 33件全てで`gen2_gc=False` → **完全に排除**
- **仮説(d)OSQPフルセットアップ(制約次元変化)**: `nseg`は33件全てで`(0, 20, 0)`固定・`nseg_changed=False` → **完全に排除**(コリドーは常に全waypoint1区間のまま複雑化していない)
- **仮説(b)CPU競合**: **唯一残った容疑**。ほとんどのケースで`mpc`・`mpc_setup`・`mpc_corridor`がほぼ同時に(同一比率で)膨らんでおり、特定区間だけが単独で膨らむ内因パターン(仮説dのような)ではなく、区間を問わず同じ計算が遅くなる外因パターンと一致する。典型例:
  ```
  [PERF-SPIKE] loop=13329 loop_mod100=29 work=32.43ms budget=13.89ms cache_builds_diff=0 nivcsw_diff=13 gen2_gc=False gen2_gc_dur=0.00ms nseg=(0, 20, 0) nseg_changed=False | mpc=31.13 mpc_corridor=28.64 mpc_linearize=0.65 mpc_setup=30.01 mpc_solve=0.81 ...
  ```
  `mpc_corridor`が通常の2-4msから20-28ms(約7-10倍)へ膨らんでいるが、`nseg`不変(=処理内容自体は変わっていない)であり、コリドー最適化(256/258節)自体の退行ではなく、同じ軽い計算が何らかの理由で遅く実行されたことを示す。`nivcsw_diff`(不随意コンテキストスイッチの前サイクル差分)はスパイク時5〜25(全区間平均の1周期あたりnivcsw=3.45を上回る値が大半)で、CPU横取り(スケジューリング競合)を示唆する状況証拠だが、直接の因果証明ではない。
  
  1件(loop=24192)のみ`pubtail`(publish関連)が単独で膨らむ別系統のパターンも見つかり、corridor系スパイクとは別の副次的な遅延源が存在する可能性を示す小さな追加所見として記録した。

# 確認したいこと

1. 今回の改善(4基準中2基準が新規合格、他2基準も大幅改善)が「出力制限解除」という単一の環境変化と時系列的に整合するという解釈は妥当か。1回の比較実測のみでこの因果関係についてどの程度主張してよいか。
2. `[PERF-SPIKE]`の帰属分析で仮説(a)(c)(d)を完全に排除し、仮説(b)(CPU競合)のみを状況証拠(nivcsw_diff上昇・複数区間の同時膨張)で示唆する、という進め方は方法論として妥当か。CPU競合をより直接的に証明する追加の計装や実験(例: taskset/CPUピニングでの対照実験、nice値変更、AWSIM側の負荷を意図的に変える等)はあるか。
3. 総合判定が依然不合格(2/4基準未達)の状況で、次に取るべき行動として何が妥当か: ①再現実験(同一条件で複数回計測し統計的な確度を上げる)、②60Hzへ後退して同様の改善傾向があるか確認、③CPU競合を直接証明/軽減する実験(CPUピニング等)を試す、④現状の改善幅(基準の半分は既に達成)を踏まえてボーダーラインとして72Hzを試験的に採用する、のどれを優先すべきか。
4. `pubtail`単独スパイク(1件のみ観測)は無視してよいレベルの外れ値か、それとも別途調査すべき兆候か。
5. その他、この報告全体を通して見落としている懸念があれば指摘してください。
