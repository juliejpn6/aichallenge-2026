あなたは自動運転レーシングカート(ROS2 Humble / Autoware、spatial MPCで制御)のソフトウェアアーキテクトです。72Hz化(現状40Hz)調査の続報です。前回相談した「work基準の関心分離+C4双方向アフィニティ実験」の後続として、①前回の確認事項4(MPC.pyクラッシュ)の修正、②C4のwall基準悪化(4条件中最悪)の原因特定と是正策(C4')の実装、③直接証拠のための追加計装、を実施しました。C4'はまだ実測していません。実測前に設計・計装の妥当性を検証してほしいのと、実測時の判断方針を相談したいです。

# 前提(再検討不要、確定済みの経緯)

- C0(無介入)/C1(governor=performance)/C2(コンテナ全体cpuset隔離、不採用)/C3(mpc_controllerプロセス単体アフィニティ)/C4(双方向アフィニティ、他ノードをtasksetで補集合コアへ退避)まで実測済み
- 分離後基準(`work_cpu`>予算≦0.1% + 改訂p99 + 連続超過≦3周期 + eff_rate≧70Hz)で判定すると**C4が4基準すべてに合格する初の条件**だった。一方、旧wall基準(`work`>予算)ではC4が4条件中最悪(1.134%)という逆説的結果で、この解釈が前回の相談事項だった
- 前回提示した未検証仮説: 「C4は他ノードを12論理コア(0,1,6-15)へtasksetで押し込めたことで、それらノード同士の間で新たな競合が生まれ、DDS通信・コールバック配送遅延を介してmpc_controllerの`_control()`呼び出し開始タイミング自体を後ろ倒しにしている可能性がある」

# 今回実施したこと

## Part A: MPC.pyクラッシュの修正(前回の確認事項4への対応)
C4実験中(約10回中1回)に`core/MPC.py`の`_stage_data()`で`xmin_dyn[nx::nx] = lb`が`ValueError: could not broadcast input array from shape (20,) into shape (1,)`でクラッシュしノードが落ちる事象があった。原因を高確度の仮説として特定: `get_control()`が確定させるN(非循環経路[ピット等]では残りwaypoint数で縮小しうる)より後に`_stage_data()`冒頭の`wp_id_offset`加算が効くため、非循環経路の終端付近で`wp_id+N`が`n_waypoints`を超え、`_corridor()`が返す`lb`/`ub`の長さがNと一致しなくなる。合成データで同一エラーを再現し裏付けた。根本原因(`wp_id_offset`加算タイミング)の修正は起動シーケンスに触れるため別途の検討に委ね、今回は止血として`_stage_data()`に長さ不一致検出時の安全側整形(`_resize_to_length`)を追加した。長さ一致時(通常時)は分岐に入らず既存挙動に一切影響しない(コリドー等価性回帰1518件+回帰スイート全体2868件PASSで確認)。

## Part B-1: simulator侵入の事実確認
`ps -eLo pid,psr,pcpu,comm`でスレッド単位のCPUコア割り当てを直接観測し、**simulator(AWSIM)コンテナのcpusetが未設定(0-15番コア無制限)のため、AWSIMのスレッドがmpc_controller専有のはずの論理コア(2-5)へ実際に侵入して動いているサンプルを複数回観測した**。C1〜C4はいずれもsimulator側のコア制限をしておらず、autoware側だけをどれだけ隔離してもこの侵入経路は防げていなかった。これが上記「未検証仮説」とは別の、より直接的なC4悪化要因である可能性が高いと判断した。

## Part B-2: run_delay計装
`/proc/<pid>/task/<tid>/schedstat`の第2フィールド(ランキュー待ち累積ns)を直接読み、wall-cpuギャップの原因をランキュー待ちそのものと数値で結びつける計装を追加した。`kernel.sched_schedstats`が無効(既定)だと全フィールドが常に0になり見かけ上「読めてしまう」ため、可用性はsysctl自体の値で判定し、ファイル読み取り成功では判定しないようにした。`[PERF-SPIKE]`(スパイク発生時の1周期詳細ダンプ)に`run_delay=`、`[PERF-RUSAGE]`(定期窓集計)に`run_delay_avg=`/`run_delay_max=`を追加。あわせて`[PERF-DT]`にdt p99.9/maxを参考記録として追加(判定基準には使わない)。単体テストで可用性判定ロジック・差分算出・窓集計・ログ配線を確認済み(実機/実データでの検証はまだ)。

## Part B-3: C4'実装(simulator隔離)
C4の構成(mpc専有コア2-5・他autowareノードはtasksetで0,1,6-15)に加え、**simulatorコンテナにも同じ補集合cpuset(`0,1,6-15`)を追加**し、「mpc専有コア」「他autowareノード」「simulator」の三者を完全に分離するdocker-compose override(`docker-compose.c4prime-experiment.yml`)を作成した。simulator側にはCPU「クォータ」制限(cpus:上限値)は付けていない(レンダリング等の負荷特性がautowareノード群とは異なるため、コア範囲の隔離のみに留めた)。

## 追加分析: [PERF-SPIKE]と[HOTSPOT-DEVIATION]の時刻相関
「wall超過はコーナリング演算(corridor/raster)自体が重いコーナーに紐づくのでは」という仮説を検証するため、実走ログ1本で`[PERF-SPIKE]`(実ダンプ6件)と`[HOTSPOT-DEVIATION]`(特定waypointでの大きな横偏差、5地点×周回反復で計35件)の発生時刻をepoch秒で突き合わせた。**結果: 6件中2件だけが同一コーナー(wp=258)通過時のHOTSPOT-DEVIATIONと数秒以内(0.2s, 2.46s)で近接し、残り4件は最寄りのHOTSPOT-DEVIATIONからも20〜37秒離れていて無相関**だった。近接した2件も支配的コスト要因(traffic_ot処理 vs mpc_solve+prep)がバラバラで共通の因果を示さない。6件それぞれの支配的コストはmpc_setup+corridor / raster+prep / traffic_ot突出(39.99ms) / raster+prep+sleep / icc+corridor / prep+mpc_solveと毎回異なっていた。

# 確認したいこと

1. **C4'の実験設計は妥当か**。simulatorをcpusetのみで隔離しCPUクォータは付けない、という判断は理にかなっているか。それとも先にsimulator側にもcpus quotaを付けて切り分けるべきか、あるいはsimulatorを物理的に別プロセス/別ホストへ分離してから検証すべきか。
2. **[PERF-SPIKE]と[HOTSPOT-DEVIATION]の無相関という結果をどう解釈すべきか**。「単一のホットスポット(重いコーナリング演算)ではなく、確率的なCPU競合が原因」という解釈は妥当か、それとも計装をさらに追加してから判断すべきか(例: cgroup `cpu.stat`のthrottled_time、`perf stat`でのcontext-switch/cache-miss計測等)。
3. **run_delay計装の設計は妥当か**。特にsysctl値での可用性判定(ファイル読み取り成功では判定しない)という方針、`/proc/self/task/{tid}/schedstat`を優先し`/proc/self/schedstat`にフォールバックする構成に見落としはないか。
4. **C4'実測時の判断方針**: run_delayが有意な値を示した場合(ランキュー待ちが実証される)と、示さなかった場合(CPU競合ではなく別要因、例えばDDS配送遅延そのもの)とで、次に取るべき調査の分岐をどう設計すべきか。
5. **総合判断**: C4'実測(12分間)を回す前に、優先して埋めておくべき計装や仮説検証はあるか。それとも現状の計装(work_cpu・run_delay・PERF-SPIKE詳細ダンプ)で十分実測に進んでよいか。
6. その他、この報告全体を通して見落としている懸念があれば指摘してほしい。
