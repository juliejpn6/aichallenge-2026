## 現在残っている5つの課題候補

### ① wp340-40帯(周回境界)の新ホットスポット
Set B予選ログ3本全てで、周回境界をまたぐwp341・wp348・wp10のringingが一貫して大きい(初期振幅wp10: 15.41°/18.57°/13.71°)。既知のwp269-282系ホットスポット(セッション依存が強くwp277は3本中1本でしか明瞭に現れない)とは対照的に、**特定の対戦車状況に依存しない再現性の高い問題**。減衰率もδ≈0.27-0.69と他箇所(δ=0.823)より低く収束が遅い(目算3〜8.5周期)。原因未調査(コース形状・曲率変化率との対応関係は未確認)。

### ② OTミッドコーナー側反転による蛇行
0804-06ログの1周目最初のコーナー(wp65-78、kappa最大-0.188)で、OT側(`_ot_side`)がコーナー深部で約1秒のうちにside=-1→side=1へ反転し、ekf_eyが-1.01m→+0.81mの約1.8mスイングを起こした。複数対戦車(obs=2、n_dynobs=14)存在下でengage対象選択が短時間で入れ替わったことが原因と見られる。**switchback/rescue適格性(`_switchback_eligible`/`_rescue_eligible`)は過去(design_docs 82/83節)に「`cleared`判定周りへの安易なガード追加」が衝突4.3倍・完走ラップ半減という重大リグレッションを招いた経緯があり、以降この領域への変更は厳しく制限している**。今回の現象がswitchback機構自体の問題か、通常のengage対象選択(`fwd_vid`選定)の揺れによるものかも未切り分け。

### ③ FAILSAFEウォッチドッグの構造的限界
`docker compose pause/unpause`で764ms級の全ノード同時停止ストールを走行中に人工再現(dev3、8回注入)したところ、検知率は8/8(100%)だが衝突が1件発生(既知ホットスポットwp269-282、0.8s級ストール時、最終的にSTUCK復帰で自力回復)。FAILSAFEは「プロセスが停止から復帰した後」にしか反応できない単一プロセス内蔵型ウォッチドッグであり、停止中の物理的逸脱(コーナー進入中の慣性走行による壁接近)は実装の巧拙によらず原理的に防げないと判明。真に防ぐには停止したプロセスと独立に動作する外部監視(別プロセス/コンテナでのハートビート監視+独立した緊急停止コマンド)が必要という結論に至ったが、設計は未着手。

### ④ q_ey_overtake/q_ey_pitの再チューニング
Q[e_y]ベース値が3M時代→700k→200kと下がる間、`q_ey_overtake`(5,000,000)・`q_ey_pit`(50,000,000)は据え置かれ、通常比の倍率が1.67倍/16.67倍(3M時代の設計時想定)→25倍/250倍(現行)へ膨張していた。dev4(4台)で5,000,000(現行)/1,000,000(中間)/330,000(比率保存候補)を検証したが、330,000は起動ハングで欠測、5,000,000 vs 1,000,000は結果が混合(wp269-282ホットスポットは5,000,000が良好、一般ringing初期振幅は1,000,000がやや良好)。結論を保留し現行値を維持中。

### ⑤ Q[e_y]/Q[e_psi]のn数積み増し
上記の通りQ[e_y]=200,000の効果はn=3で約2倍のばらつきが判明しており、より高い確度で結論づけるには追加のn数が必要な状態。

1. 上記5課題の優先順位付けについて見解がほしい。判断材料として、①緊急度(安全性への直接的な影響度)②難易度・所要時間③締切(内部締切08/25まで残り20日)への適合性④過去の教訓(特にswitchback領域の慎重さ)を明示的に考慮してほしい
2. ②(OTミッドコーナー側反転)は、82/83節の教訓がある領域に隣接しているが、今回の現象は「switchback機構自体」ではなく「engage対象選択の揺れ」が原因の可能性もある。この切り分けを安全に行うための調査手順(コードを変更せずログ解析だけで診断する方法があれば)を提案してほしい

4. ①(wp340-40帯)は着手しやすそうに見えるが、見落としている落とし穴があれば指摘してほしい
5. ④・⑤は「地味だが重要」な保留事項だが、①〜③と並行して進めるべきか、それとも完全に後回しにすべきか
