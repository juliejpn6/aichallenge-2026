あなたは自動運転レーシングカート(ROS2 Humble / Autoware、spatial MPCで制御)のソフトウェアアーキテクトです。以前あなたが「Go(72Hzへの実際の切替と実測へ進んでよし)」と最終判定した72Hz切替(40Hz→72Hz)について、実際に`control_rate`を72.0へ変更し実機シミュレータで評価しました。結果は**不合格**でした。次にどうすべきか助言をください。

# 前提(再検討不要、確定済みの経緯)

- 40Hz→72Hzのレートスケーリング機構(周期数の線形換算・EMA/ローパスゲインの指数換算、23箇所)は実装・レビュー済みで、実機で全24行の`[RATE-SCALE]`ログが正しい換算値(40Hz→72Hz)になることを確認済み(1行の不一致も無し)
- dt(`_control()`呼び出し間隔)の超過判定にマージンε(健全なrclpy.Rateジッタを吸収するための余裕)を導入し、単一車両ベースライン(約10.7分)+対戦車あり2両ベースライン(約12分)の実機実測から**ε=85ms**と較正済み
- コリドー計算(mpc_corridor)は別スレッドで等価最適化済み(ベクトル化+衝突判定メモ化、16.7倍高速化・ビット等価性100%)で、今回の72Hz評価でも退行は無い(下記参照)

# 今回実施したこと(Phase 5: 72Hz切替の実測)

1. `config.yaml`の`control_rate`を72.0へ変更
2. ノード構築のみの軽量チェックで`[RATE-SCALE]`全24行を採取し、想定通りの72Hz換算値(例: `hold_cycles` 60→108周期、`accel_low_pass_gain`/`steer_low_pass_gain` 0.35→0.2128、`pf_over_budget_s` 0.025000s→0.013889s)であることを確認(1行も不一致なし)
3. 短時間(約2分)の実走行でrclpy.Rateの初動ジッタを40Hzベースラインと比較 — 絶対値ベースで著しい悪化は無し(max dt 42〜54ms、40Hzベースラインのmax 40〜179msと同等以下)と判断し継続
4. 同一シナリオ(`make dev`、単一車両、AWSIM+Autoware)で約9.7分(58窓・41,760周期)の本実測を実施

# 実測結果(不合格)

| 基準 | 目標 | 実測 | 判定 |
|---|---|---|---|
| 処理時間: work>13.9msの割合 | ≦0.1% | **6.41%**(2,677/41,760周期) | ❌ 不合格(64倍) |
| dt: p99 | ≦20.85ms(予算×1.5) | 平均34.95ms・最悪41.84ms | ❌ 不合格(58/58窓すべて未達) |
| dt: 連続超過(dt>予算+ε=85ms) | ≦3周期 | 0(全窓) | ✓ 合格 |
| eff_rate | ≧70Hz | 平均68.69Hz(65.65〜71.02Hz) | △ 51/58窓(87.9%)が未達 |

**4つのAND条件のうち2つが明確に不合格、1つが大部分の窓で未達、1つのみ合格。**

# 原因の切り分け(重要な発見)

work avg=9.17ms(13.9ms予算の約66%)自体は健全で、これは設計書が事前に見積もっていた「約72%」の想定とほぼ整合していた。**問題はwork maxのスパイク**(平均45.41ms・最悪65.30ms、予算の3〜4.7倍)であり、40Hzの25ms予算では吸収できていたスパイクが、72Hzの13.9msという狭い予算では致命的な超過になっている。

`[PERF]`の区間別内訳(worst-caseの実ログ抜粋):
```
[PERF] n=720 work avg=10.6ms max=45.3ms >25ms=110回 | mpc a=7.8 m=40.5 | mpc_corridor a=4.1 m=36.6 | mpc_linearize a=1.4 m=17.4 | mpc_setup a=6.9 m=38.8 | mpc_solve a=0.5 m=4.6 | prep a=1.2 m=23.7 | pubtail a=1.1 m=9.4 ...
[PERF] n=720 work avg=10.3ms max=62.8ms >25ms=90回  | mpc a=7.6 m=45.7 | mpc_corridor a=4.1 m=38.9 | mpc_linearize a=1.3 m=5.9  | mpc_setup a=6.8 m=42.9 | mpc_solve a=0.4 m=3.4 | prep a=1.2 m=23.5 | pubtail a=1.0 m=8.2  ...
```
最大の寄与源は`mpc_setup`(線形化+QP準備、avg 6.8-6.9ms・max 38.8-42.9ms)と`mpc_corridor`(avg 4.1ms・max 36.6-38.9ms)。`mpc_corridor`のavg値は別スレッドで最適化済みの40Hzベースラインとほぼ同水準(退行なし)であり、**今回のスパイクの主因はコリドー計算ではなくmpc_setup(線形化ループ)側**である可能性が高い。

**εの仕組み自体は正しく機能した**(連続超過基準は合格) — 今回の不合格は「rclpy.Rate自体のジッタ」ではなく「MPCソルバー周辺(mpc_setup/mpc_corridor)の処理時間スパイク」が原因であり、これはεでは吸収できない別種の問題である。

# 確認したいこと

1. この不合格判定・原因の切り分け(ジッタではなく処理時間スパイクが主因)は妥当か。見落としている解釈はないか。
2. 設計書が元々用意していた段階的フォールバック(`control_rate: 60.0`、予算16.66msで再測定)を次に試すべきか、それとも先に`mpc_setup`のスパイクの根本原因(どの条件で発生するか)を調査してから判断すべきか。
3. `work avg`(9.17ms、予算の66%)は健全なのに`work max`(65.30ms、予算の4.7倍)だけが問題という非対称な状況は、典型的にどのような原因(GC・OSスケジューリング競合・特定waypoint/OT状態での計算量爆発・OSQPのウォームスタート失敗等)を疑うべきか。
4. `eff_rate`(平均68.69Hz、70Hz未達が88%の窓)は`max_consec_over=0`と矛盾しないように見えるが、この2指標の関係(キャッチアップ効果でeff_rateは鈍いという259節の設計判断)を踏まえると、今回の未達をどの程度深刻に見るべきか。
5. その他、この報告全体を通して見落としている懸念があれば指摘してください。
