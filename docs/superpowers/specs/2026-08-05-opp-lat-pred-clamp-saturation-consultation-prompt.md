# 背景

ROS2/Autoware自律走行レーシングカート(spatial MPC制御、40Hz制御ループ)の
オーバーテイク(OT)処理に、対象車の横方向速度を自前でEMA推定し、通過予測
時刻まで外挿して必要最小オフセットを計算する機構(候補①、既に実装・
本番投入済み)があります。この機構に重大な疑わしいパターンが見つかった
ので相談します。

## 現状の実装

```python
# 対象車の横位置(_c_lat)は_scan_traffic内で以下のように計算される:
wp_i, s_obs = self._closest_wp_and_s(cx, cy, prev_idx=self._wp_match_prev.get(vid))
self._wp_match_prev[vid] = wp_i
wp = rp.waypoints[wp_i]   # 対象車の世界座標に最も近いwaypoint
lat = math.cos(wp.psi) * (cy - wp.y) - math.sin(wp.psi) * (cx - wp.x)
# ↑ 対象車の位置(cx,cy)を、対象車自身に対応するwaypointの方位角(wp.psi)基準の
#   局所座標系(横方向)へ変換する式(Frenet変換の横方向成分)

# min_needed_mag計算(別関数、OVERTAKING中毎周期):
if (self._ot_opp_lat_prev is not None
        and self._ot_opp_lat_prev_vid == self._ot_target_vid):
    dt = 1.0 / control_rate
    raw_lat_vel = (opp_lat_now - self._ot_opp_lat_prev) / dt   # 前周期からの差分
    raw_lat_vel = clamp(raw_lat_vel, -2.0, 2.0)                # ±2.0m/sへクランプ(301節で追加)
    if self._ot_opp_lat_vel_ema is None:
        self._ot_opp_lat_vel_ema = 0.0                          # 0.0から開始(301節で追加)
    self._ot_opp_lat_vel_ema += 0.05 * (raw_lat_vel - self._ot_opp_lat_vel_ema)  # EMA(alpha=0.05)
opp_lat_pred = opp_lat_now + self._ot_opp_lat_vel_ema * t_reach  # t_reachは最大1.5秒
```

`_closest_wp_and_s`は対象車の世界座標に最も近いwaypointを検索する関数
(`prev_idx`は前回値をヒントとして渡す最適化)。

## 問題(dev3実地検証35分、596サンプルで発見)

`opp_lat_pred`の値を集計したところ、**24%(146/596件)がクランプ限界近く
(-2.5未満)に張り付いており、しかも負方向へ極端に偏っている**(<-2.5が
146件に対し>2.5はわずか5件)。正常域(-1.0〜1.0)はわずか23%(136件)。

| 範囲 | 件数 |
|---|---|
| 正常域(-1.0〜1.0) | 136 |
| 中程度(絶対値1.0〜2.5) | 309 |
| クランプ限界近く(<-2.5) | 146 |
| クランプ限界近く(>2.5) | 5 |

**具体的な問題事例**: 対象車が`[GHOST-BLOCK]`ログで`v=0.00`(ほぼ完全停止)
と確認されている周期に、`opp_lat_pred=-2.912〜-2.914`という値が2周期連続で
観測されました。停止している相手の横速度はほぼゼロのはずなのに、EMA推定が
クランプ上限(±2.0m/s)近くまで張り付いていました。alpha=0.05のEMAで単発
ノイズがこの水準まで持続的に張り付くには、生の差分値(`raw_lat_vel`)が
複数周期にわたって継続的にクランプ上限に達している必要があり、単発の
測定ノイズでは説明できません。この直後にGHOST-BLOCK→STUCKが発生しました
(因果関係は未確定、n=1)。

なお発生区間(wp280-282)は既知の曲率のあるホットスポットで、実測
`kappa=-0.109〜-0.178`を確認しています。

## 仮説(未検証)

1. **waypointインデックス切り替えによるフレーム回転混入**: `_closest_wp_and_s`は
   対象車の世界座標に最も近いwaypointを検索します。もしEKF/V2X位置推定の
   わずかなノイズで、対象車が2つの隣接waypoint境界付近を行き来すると、
   `wp_i`が周期ごとに切り替わり、`wp.psi`(waypointの方位角)が変わるため、
   対象車が世界座標で静止していても`lat`の値がジャンプしうる。曲率が大きい
   区間ほど隣接waypoint間の`psi`差が大きく、影響も大きい。
2. OT中の頻繁な側選択・幅寄せ自体が、この量を本質的にノイズの多い指標に
   している。
3. クランプ値(±2.0m/s)自体が実際に妥当な範囲より緩すぎる。

## 相談したいこと

1. 上記3仮説のうち、どれが最も可能性が高いと考えますか? 特に仮説1
   (waypointインデックス切り替え)について、`_closest_wp_and_s`の実装を
   見ずに判断するのは難しいと思いますが、一般的なFrenet変換+最近傍
   waypoint検索の組み合わせでこの種の不連続性が起きることは、自動運転の
   経験則としてよくあることでしょうか?
2. 対処法として何が考えられますか? 候補:
   a. waypointインデックスが切り替わった周期は、その周期の`raw_lat_vel`を
      信頼せず(前回のEMA値を維持する、または0とみなす)スキップする。
   b. `_closest_wp_and_s`にヒステリシス(前回のwp_iから大きく変化しない限り
      切り替えない)を追加する。
   c. `lat`自体ではなく、世界座標系での対象車位置の差分(自車のFrenet変換を
      経由しない、より直接的な横方向速度推定)を使う。
   d. クランプ値をさらに厳格化する(±2.0→±1.0等)。
3. 3台のうちd2/d3(64/198件・70/230件がクランプ限界近く)がd1(17/168件)より
   顕著に悪いことについて、何か推測できることはありますか? d1は自車(ego、
   v_max=20km/h、常に他車を追い越す側)、d2/d3は相手にされる側(追い越される
   側、v_max=15-17km/h)という非対称な役割の違いが関係していると思いますか?
4. このプロジェクトの慣習として、コード変更前にまず既存ログのオフライン
   分析(反実仮想の机上検証、コード変更ゼロ)で仮説を検証してから実装する
   段取りを踏んでいます。今回の仮説1を検証するには、どのような分析が
   有効だと考えますか(例: 生の`lat`値の時系列とwp_iの遷移を突き合わせる等)?

以上、率直な意見をお願いします。
