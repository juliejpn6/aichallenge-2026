# 実装の要約

## Phase 1: マップ幾何不変性の調査・固定

`wp._fs_line_cache`(Phase 3-1で導入したピクセル座標キャッシュ)は、マップ幾何(origin/resolution/width/height)が起動後不変であることに依存している。エージェントに調査させた結果:

- `core/map.py`にはこれら4値を書き換えるメソッドが存在しない(`reset_map()`/`add_obstacles()`等は`data`のみを変更)
- `mpc_controller.py`の`self._map`は起動時に1回だけ構築され(`_initialize()`内)、以降どこにも再代入されない
- reference_path再構築(`_create_reference_path_from_autoware_trajectory`、`update_by_topic`有効時に100周期ごと)も**同一の`Map`インスタンス**をそのまま新しい`ReferencePath`へ渡す(新しいwaypoint集合が構築されるだけで、マップ自体は差し替わらない)

**結論: 現行コードでは不変。** それでも将来この前提が崩れても静かに誤った座標を使い続けないよう、キャッシュ構築時にマップ幾何をタプルとして記録し、参照のたびに(タプル比較のみ、数十ns)現在の幾何と照合する軽量ガードを追加した。不一致時は例外ではなく、キャッシュを破棄した上で`_compute_free_segments_scalar`(素朴な参照実装)へこの呼び出しに限りフォールバックする(次回呼び出し時に新しい幾何で自動的に再構築される、自己修復設計)。人工的にマップのoriginを書き換える単体テストで、ガードの発火・フォールバック・次周期での自己修復を確認した。

## Phase 2: case_idx=125の名前付きゴールデン昇格

差分ファジングのコーパスは`case_idx`+期待値のみを保存し、グリッド自体はシードから都度再構築する設計(191MB→169KBに圧縮するため)のため、将来コーパスを再生成すると「実績のある地雷原」——Phase 3-2で後ろ向きDPが実際に等価性を破った実例(case_idx=125)——が静かに消えるリスクがあった。

この入力を壁配置ごとハードコードして`corridor_golden_cases.py`へ`10_fp_absorption_tiebreak`として独立保存した(シード再生成に非依存)。単に出力が凍結値と一致するだけでは「たまたま別の理由で同じ出力になった」場合を検出できないため、専用テストで**吸収現象が実際に発生していること**を直接assertする:

- horizon内n=3の2つの候補セグメント幅は単独では明確に区別される: `4.199999999999999 != 4.2`
- n=0(選択セグメント)・n=1・n=2の部分和(旧実装と同じ前向き=左結合の逐次加算で再現、約21.2)に、これら2つの幅をそれぞれ加算すると、**両方とも同一の浮動小数点値`25.400000000000002`へ丸め吸収される**

この保証が崩れたら(=もう吸収が起きなくなったら)テストが明示的に失敗し、「このケースはもはやDP化の罠を検出できないため、別の吸収現象を示す新しいケースへ差し替える必要がある」というメッセージを出すようにした。

`calculate_combination_total_segment_length`の加算行の直上には以下の警告コメントを追加した:

```python
# 警告: この加算の順序(前向き・左結合)はタイブレークの一部である。
# DP化・加算順の並べ替え・math.fsum・numpy sum への置換は、浮動小数点の
# 吸収により選択結果を変える(実証: golden case 10_fp_absorption_tiebreak、
# test_case_10_actually_exhibits_floating_point_absorption参照)。
total_segment_length += dist(ub_fs[0], ub_fs[1], lb_fs[0], lb_fs[1])
```

さらに、関数の主要ループ直上には、DP化を試みて破棄した経緯(前向き左結合 vs 後ろ向き右結合の結合則崩れ、具体的な吸収の数値例、「itertools.productの辞書式順序+前向き左結合累積」が生命線であること)を詳述する、より長い警告ブロックも追加した。

## Phase 3: line_aa OOBプロパティテストの常設化

前回実施した一度きりの実験(5マップサイズ×10,000件超のランダム境界ケース、`line_aa`が範囲外ピクセル座標を返すか検証)を、`test_line_aa_oob_property_254.py`として常設回帰テストへ格上げした。CI実行時間を考慮しシード固定1,500件に抑えた(5マップサイズ×300件、実行時間約3秒)。`Map.w2m()`でクランプ済みの入力座標を`line_aa`へ渡し、返るピクセル座標が全て範囲内であることを検証する。違反0件。skimageバージョン更新時にこのテストが自動で再検証し、失敗時は他の`line_aa`呼び出し箇所(`has_collision_in_line`等)への実行時クリップ追加を検討するよう、docstringに手順を明記した。

## Phase 4: 小粒の防御・文書化(4件)

1. **キャッシュ構築時クリップ**: `_fs_line_cache`構築時(初回waypoint参照時の1回のみ)に`np.clip(x_arr, 0, width-1)`/`np.clip(y_arr, 0, height-1)`を追加した。現状は恒等操作(等価性回帰1510件で確認済み)だが、将来のskimage仕様変更に対する静的パスの構造的な安全策として追加した。周期あたりコストはゼロ。

2. **キャッシュ構築タイミングの確認**: 遅延構築(各waypointが初めてホライズンに入った周期にのみ発生)であることを確認した。全waypoint分のプリウォームは`ReferencePath.__init__`という広く使われるコンストラクタへの変更を要し、そのリスク(既存の複雑な初期化フローへの影響範囲が読み切れない)を避けるため見送った。代わりに`[PERF-CORRIDOR]`へ`cache_builds`カウンタを追加し、初回構築が実際に何回・どの周期で起きているかを可視化できるようにした(通常は起動直後の数周期、またはreference_path再構築時のみ増加し、巡航中はゼロが継続するのが正常という期待値を単体テストで固定した)。

3. **計測カウンタの意味注記**: Phase 3-2導入前(itertools.product+毎組み合わせごとの`has_collision_in_line`再計算)はlazy(衝突が見つかった時点で以降のペアを評価せず早期打ち切り)だったのに対し、Phase 3-2後(隣接レイヤー間ペアの事前メモ化)はeager(列挙結果に関わらず全ペアを常に事前計算しきる)である旨をコード内コメントで注記した。新実装の`collision_checks`は常にΣS_i×S_{i+1}の固定上限値であり、旧実装のようにケースごとの早期打ち切り具合で変動する値ではない。

4. **DFS設計の文書化(実装禁止、design_docs 258節に記録)**: インデックス順DFS+前方接頭辞和の共有+衝突サブツリーのみの刈り取りは、葉の訪問順が`itertools.product`の辞書式順序と一致し接頭辞共有が左結合累積とビット同一のため、理論上は等価性を保ったままO(S^D)の実列挙を削減できる。**ただしbranch-and-bound(スコア上界による劣枝刈り)は明確に禁止**とした——厳密算術で劣る枝がFP吸収により最良とタイになり列挙順で勝つケース(`10_fp_absorption_tiebreak`と同型)の選択を変えるため。現時点で実装しない理由: 実測で残コストが小さい(合成密集ケースD=5層・240組で全体3.22ms)。

## Phase 5: 実測値の解釈記録

design_docsに、合成密集ケース(D=5層・240組)で旧実装が**53.87ms**を要していた事実が、過去に実環境で観測された「平常の3〜5倍」スパイク(30〜50ms)を組み合わせ探索の爆発として説明可能であることを1段落追記した。72Hz切替判定の際、処理落ち率はこの前提(コリドー計算由来の突発的スパイクは本最適化で主要因としては解消済み)の下で解釈すべきことを記録した。
