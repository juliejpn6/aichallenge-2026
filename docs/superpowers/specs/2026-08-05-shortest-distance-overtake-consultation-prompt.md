# 背景

ROS2/Autoware自律走行レーシングカート(spatial MPC制御、OSQPソルバー、40Hz制御ループ)
のオーバーテイク(OT)処理を改善しています。以下は現状の設計と、次に検討している
改善案の草案です。フィードバック・改善案・見落としているエッジケースがあれば
教えてください。

## プロジェクトの制約

- コース形状(waypoint配列、各区間の弧長・曲率)は既知で、区間ごとの計画速度
  プロファイルも事前に持っている(`ref_vel_configulator`)。
- 対戦車の位置・速度はV2X的な仕組み(`_scan_traffic()`)で毎周期取得できる。
  ただし対戦車自身の将来の挙動(加減速するか等)は分からない——単純な現在速度の
  等速仮定が妥当な想定。
- 制御コードは`_control()`という巨大な1関数(数千行)内にほぼ全てのロジックが
  ある。1周期40Hz(25ms)で呼ばれる。
- このOT機構は過去100セッション以上にわたり慎重にチューニングされてきた
  領域で、迂闊な変更は過去に重大リグレッションを招いた実績がある
  (安全マージン系の判定ロジックは特に慎重)。

## 現状の設計

### ①ENGAGE判定
対象車が前方近くにいて、自車の方が速く、経路上にいる、等の複数条件
(`_evaluate_engage_readiness`)を満たすと`OVERTAKING`状態へ遷移する
(`ENGAGE`)。この判定には既に「相手が完全停止/低速の場合、コース速度
プロファイルを積分して自車が追いつく時刻を予測する」関数
`_predicted_time_to_wp(from_wp, to_wp, max_dist)` が実装済みです:

```python
def _predicted_time_to_wp(self, from_wp: int, to_wp: int, max_dist: float):
    """コース既知の区間速度プロファイル(ref_vel_configulator)を弧長積分し、
    自車が特定waypointへ到達するまでの予測時間を計算する。
    stopped_opponent(相手が完全停止/低速)の場合、相手の位置(wp)は実質固定
    であり、自車がそこへ到達するまでの所要時間は区間ごとの計画速度さえ
    分かれば経路形状から一意に計算できる。"""
    if self._ref_vel_configulator is None:
        return None
    rp = self._reference_path
    n = len(self._wp_s_cum)
    total_t = 0.0
    total_d = 0.0
    wp = int(from_wp) % n
    to_wp = int(to_wp) % n
    for _ in range(n):
        if wp == to_wp:
            return total_t
        nxt = (wp + 1) % n
        seg = float(self._wp_s_cum[nxt]) - float(self._wp_s_cum[wp])
        if rp.circular and seg < 0.0:
            seg += rp.length
        try:
            v_kmh = self._ref_vel_configulator.get_ref_vel(wp)
        except Exception:
            v_kmh = float(self._cfg.mpc.v_max)
        v = max(kmh_to_m_per_sec(v_kmh), 0.1)
        total_t += seg / v
        total_d += seg
        if total_d > max_dist:
            return None
        wp = nxt
    return None
```

**この関数は現在「相手が停止/低速の場合のみ」使われており、相手が走行中の
場合は使われていません**(その場合は`_engage_dist_dynamic`という、自車の
絶対最高速度で一定走行すると仮定する簡易近似にフォールバックします)。

### ②オフセットランプ(横方向オフセットの立ち上げ)
ENGAGEが成立すると`_ot_state = "OVERTAKING"`になり、`_a_target`(オフセット
目標のON/OFFフラグ)が1.0になります。実際の横方向オフセットは`_ot_alpha`
(0→1のブレンド係数)を通して徐々に立ち上がります:

```python
# 相手が停止/低速の場合: ランプを省略し即座にフルオフセット
if _a_target > 0.0 and _stopped_opp:
    self._ot_alpha = 1.0
# それ以外(相手が走行中): 0.5秒かけて漸増
else:
    _ramp_step = dt / max(self._ot_ramp_time, 1e-3)  # ot_ramp_time=0.5秒
    self._ot_alpha += float(np.clip(_a_target - self._ot_alpha, -_ramp_step, _ramp_step))
    self._ot_alpha = float(np.clip(self._ot_alpha, 0.0, 1.0))
self._mpc.lateral_blend = self._ot_alpha
_cur_off = self._ot_alpha * self._mpc.lateral_target  # 実効オフセット
```

**つまり現状: ENGAGEが成立した瞬間(相手がまだ数秒先にいても)から、
オフセットランプが立ち上がり始めます。** 相手が走行中の場合、実際に横に
並ぶまで数秒かかることも多く、その間ずっとレースラインを外れた状態
(オフセット非ゼロ)で走行することになります。

### ③必要最小オフセットの大きさ(本日実装済み・別軸)
`_ot_alpha`が最終的に到達する目標値`_target_mag`(オフセットの**大きさ**)
は、対象車の予測横位置を使って必要最小限に絞る仕組みを本日実装済みです
(対象車の横方向速度をノイズ耐性付きEMAで自前推定し、通過予測時刻まで
外挿)。これは大きさの最適化であり、今回相談したいのはタイミング
(いつオフセットランプを開始するか)の最適化で、別軸の話です。

## ユーザー提案(今回検討したい改善)

> 自分の車速と相手の車速を意識した追い越しアルゴリズムを設計しましょう。
> できるだけ最短距離でオーバーテイクを遂行する。
> 相手を追い越すコーナーを推定し、そこまでは既定経路(レースライン)を
> 走行する。

つまり:
1. ENGAGE成立後も、すぐにはオフセットランプを開始しない。
2. 自車の速度プロファイル(既知)と相手の現在速度(等速仮定)から、
   「自車が相手に追いつく地点(弧長・waypoint)」——ユーザーの言う
   「追い越すコーナー」——を予測する。
3. その地点の手前(ランプ所要時間分だけ先行させたタイミング)まで、
   オフセット=0のまま既定経路(レースライン/コリドー中心)を走行する。
4. 予測地点に近づいたらオフセットランプを開始し、実際に横に並ぶ頃には
   フルオフセットに到達している状態にする。

これにより、「必要な区間だけ」レースラインを外れることになり、走行距離・
時間が最短化される、という狙いです。

## 相談したいポイント

1. **追いつき地点の予測式**: 相手の弧長位置`s_opp(0)`・速度`v_opp`(等速
   仮定)、自車の区間速度プロファイル(既知、区間ごとに`v(s)`)から、
   「`s_ego(t) = s_opp(0) + v_opp * t`となる`t`」を解く具体的なアルゴリズムを
   どう設計するのが良いでしょうか? 上記`_predicted_time_to_wp`は「固定の
   目標waypoint」への到達時間計算であり、目標waypoint自体が時間とともに
   動く(相手が走行中)場合への拡張が必要です。単純な二分探索/反復法で
   十分か、閉形式に近い解法があるか、意見をください。

2. **ランプ遅延の安全側フォールバック設計**: 予測が外れた場合(相手が
   急減速する、V2Xの速度推定が一時的にノイズる等)、オフセット開始が
   遅れすぎて横方向の危険域接近に対応できなくなるリスクがあります。
   どのようなフォールバック条件(例: 現在の相手との距離が一定値を切ったら
   予測を無視して即座にランプ開始する等)を設けるべきでしょうか?

3. **既存の関連安全機構との相互作用**: この制御コードには、対象車との
   横方向TTC(time-to-collision)を監視して危険なら強制的にオーバーテイクを
   断念させる仕組み(`lateral_ttc_monitor.py`)があります。実測では、この
   危険検知から実際の衝突までの反応時間が0.2〜0.5秒しかないケースが
   複数確認されています。ランプ開始を遅らせる設計は、この反応時間の
   乏しい安全機構とどう組み合わせるべきでしょうか(例えば、ランプ遅延中は
   TTC監視の閾値を通常より早めに発火させる、等の案は妥当でしょうか)?

4. **「既存のRAMP-BYPASS」(相手が停止/低速の場合はランプを即座にフルに
   する仕組み)との整合性**: 相手の状態(走行中 vs 停止/低速)によって
   正反対の戦略(遅延開始 vs 即時フル)を使い分けることになりますが、
   この設計は妥当でしょうか? 状態遷移が滑らかでない(相手が急に停止した
   場合など)ケースの扱いに懸念はありますか?

5. **段階的な実装・検証のロードマップ**: プロジェクトの慣習として、
   安全に関わる制御ロジックの変更は「診断ログのみ(制御への反映なし)で
   まず的中率を実測 → config gateで既定OFFから導入 → 実地でn=2以上の
   検証を経て既定ONへ」という段階を踏みます。この段取りで問題ないか、
   より良い検証手順があれば教えてください。

## 追加相談: engage_cooldownが側を区別しない問題(既存の未着手課題)

もう一件、別軸ですが関連する既存の未着手課題があります。

### 現状の設計

OTがgiveup(断念)した際、以下のように再エンゲージを一定期間ブロックする
クールダウンタイマーがセットされます:

```python
self._ot_engage_cooldown = (
    self._ot_engage_cooldown_cycles * 2   # footprint_risk起因なら2倍(≈8秒)
    if _lat_dec.footprint_risk_triggered
    else self._ot_engage_cooldown_cycles)  # それ以外は通常(≈4秒)
```

このタイマーは`self._ot_engage_cooldown`という**単一のグローバル変数**で、
側(左から追い越そうとしたか、右から追い越そうとしたか)を一切区別しません。
ENGAGE判定側でも:

```python
_cd_clear = (
    (self._ot_footprint_risk_clear_count >= self._ot_engage_debounce
     or self._ot_engage_cooldown == 0)
    if self._ot_footprint_risk_gated
    else self._ot_engage_cooldown == 0)
_cheap_ok = (self._ot_enable and (left_ok or right_ok)
             and self._ot_infeasible_latch == 0
             and _cd_clear
             and self._ot_worth_count >= self._ot_engage_debounce
             and _on_path and _ego_ready and _close_enough
             and not being_overtaken)
```

側を問わず`_cd_clear`(cooldown解除済みか)の一項目としてANDされているだけ
です。

### 問題(実測、2026-08-04)

wp211-224実測ログで、**右側からのOTがgiveupした直後、相手が(giveupとは
無関係に)左側を大きく開けたにもかかわらず、左側への即座の再エンゲージが
グローバルクールダウン(約4秒)の間ブロックされ続けた**事象を確認しています。
v_max非依存(速度を上げても解消しない、タイマーそのものの性質)。

### 相談したいポイント

1. **設計の方向性**: クールダウンを`{side: remaining_cycles}`のような辞書に
   拡張し、side別に独立して管理するのが素直に見えますが、以下の懸念が
   あります。①`footprint_risk`起因のクールダウンは「相手そのものへの
   接近リスク」に紐づくものであり、必ずしも「側」の属性ではない(相手が
   反対側にいてもリスクは残るかもしれない)。②未使用側にクールダウンを
   適用しないと、同じ理由(同じ相手・同じ状況)で即座に再ENGAGEを試みて
   同じ結果(giveup)を繰り返すリグレッションループの再発リスクがある
   (このプロジェクトでは過去に類似の往復ループが実際に問題になった
   実績があります)。この副作用リスクをどう評価すべきでしょうか?

2. **対象車ベースで管理すべきか、側ベースで管理すべきか**: 「同じ相手への
   再エンゲージ」をブロックしたいのか、「同じ側への再エンゲージ」を
   ブロックしたいのか、設計意図として整理すると、`{(side, target_vid):
   remaining_cycles}`のような複合キーの方が適切でしょうか?

3. **実装コストとのバランス**: プロジェクトの既存原則は「新規パラメータ
   0個」を志向することが多いですが、side別クールダウンには少なくとも
   状態の型変更(スカラー→辞書またはタプル×2)が必要です。最小限の変更で
   実現する設計案があれば教えてください。

以上、率直な意見・懸念点・代替案があればいただけると助かります。
