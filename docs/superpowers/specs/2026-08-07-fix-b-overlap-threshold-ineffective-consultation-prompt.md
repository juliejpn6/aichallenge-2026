# 相談プロンプト: Fix B(並走中オフセット床)のオーバーラップ判定閾値が、動機事例そのものに対して一度も発動しない

## 背景

`opp_lat_pred`(対象車横方向速度の外挿予測、V2X~13Hzを40Hz固定dtで単純差分
することによる誤差)を根本原因とするオーバーテイク時の横オフセット不足・
急変動問題への対処として、以下3段階のFixを設計・段階導入している
(design_docs/opp_lat_pred_overlap_guard_design_20260806.md):

- **Fix A'**(実装済み・dev3ローカル検証PASS済み): `opp_lat_pred`の計算方法
  そのものを根本修正(V2Xトラッカーの既存速度推定を再利用、片側利用+
  変位物理拘束)。
- **Fix B**(実装済み・オフライン検証中、本相談の対象): Fix A'だけでは
  解決しない残存ノイズへの物理的な安全網として、「並走中(縦方向
  オーバーラップ中)はtarget_mag(横オフセット目標の絶対値)を縮小させない
  床」を追加。
- **Fix C**(未着手): 並走中の離脱(giveup)保留。

Fix Bの「並走中」判定は以下のヒステリシス付きロジックで実装した:

```python
def _update_overlap_state(self, opp_ds_now):
    if opp_ds_now is None:
        return self._ot_overlapping
    enter_thr = self._along_min_length + self._ot_overlap_margin_m  # 2.0+0.5=2.5m
    exit_thr = self._along_min_length + self._ot_overlap_margin_m * 2.0  # 2.0+1.0=3.0m
    d = abs(opp_ds_now)
    self._ot_overlapping = (d < exit_thr) if self._ot_overlapping else (d < enter_thr)
    return self._ot_overlapping
```

`along_min_length=2.00m`(カート全長)は、既存の`footprint_risk`判定
(`abs(fwd_ds) < along_min_length`)と同じ物理的下限を意図的に再利用した
値で、新規の距離定数を導入しない設計方針だった。

## 発見した問題

Fix Bを正当化する2つの名前付き動機事例(design_docs §6.0・18節)を使い、
実装前にCLAUDE.md §1.4準拠のオフライン反実仮想リプレイを行ったところ、
**両事例とも一度も`overlapping`判定がTrueにならず、Fix Bの床機構が
一度も作動しなかった**。

### フィクスチャ1: dev3衝突事例(18節、`output/20260805-222055` d1、wp215→233)

| wp | side | d_min(=対象車とのds) | offset(=target_mag) | min_needed | corr_bound | overlapping | 達成率 |
|---|---|---|---|---|---|---|---|
| 215 | 1 | 9.88m | 1.054 | 3.000 | 2.429 | False | 35.1% |
| 221 | 1 | 8.74m | 0.820 | 3.000 | 0.820 | False | 27.3% |
| 227 | 1 | 10.88m | 1.426 | 2.294 | 1.426 | False | 62.2% |
| 233 | 1 | 13.02m | 0.065 | 2.287 | **-0.557**(負転落) | False | 2.8% |

wp233で`corr_bound`が負転落し、既存の168節フリーズ機構(`_ot_last_valid_
target_mag`)が期待通りに機能せず(理由未特定、フリーズ値自体が既に
低かった可能性)、offsetが0.065まで崩壊して衝突に至った、というのが
18節の元の分析。しかし`d_min`(=対象車との縦方向距離)はこの間ずっと
8.7〜13.0mで、Fix Bの`exit_thr=3.0m`を大きく上回っていた。

### フィクスチャ2: qualifying慢性未達事例(`0805-07`、wp62→118)

41サンプル中、`d_min`の最小値は**wp109の3.00m**(それでも`exit_thr=3.0m`
未満には届かない、境界ギリギリで不成立)。残りは概ね4〜13m台に分布。
offset達成率(`target_mag / min_needed`)は12.1%〜100%まで激しく変動して
いるが、この変動と`d_min`の間に明確な相関は見られない(例: wp68は
d_min=3.91mで達成率100%、wp96は同じくd_min≈4.00mで達成率22.1%)。

## 解釈(こちらの仮説、検証してほしい)

MPCは相手車に追いつく前、まだ3〜13m手前の「接近中」段階から先行して
横オフセットを立ち上げ始めている(psi_bias/offsetのランプアップが
ログから確認できる)。両動機事例の実際の不具合(offset未達・崩壊)は、
この「接近中(まだ真横ではない)」段階で起きており、Fix Bが物理的類似性の
根拠として再利用した`footprint_risk`の閾値(真横・車体長スケールの
非常に近接した状態のみを検知する設計思想)とは、そもそも捉えている
現象のスケールが1桁近く違う。

つまり、**Fix Bは「並走中(ほぼ真横)」という狭い定義のまま実装したが、
実際に対処すべき現象は「オーバーテイク接近中の広いレンジ(3〜13m)」で
起きている**という、スコープの取り違えが疑われる。

## 質問

1. この解釈は妥当か?他に考えられる説明(実装バグ、`d_min`(=`_fwd_ds`)を
   `opp_ds_now`の代理として使ったことの妥当性の問題、サンプル数不足で
   本当に近接した瞬間を見逃している可能性等)があれば指摘してほしい。
2. Fix Bの「並走中」判定を、ds(縦方向距離)ベースの閾値のまま広げる
   (例: `exit_thr`を3mではなく10〜15m程度へ)ことは妥当か?それとも
   ds単独の閾値という設計方針自体を見直すべきか(例: `state==OVERTAKING`
   であること自体を条件にする、あるいは`corr_bound`や`offset_margin`等
   別の指標を併用する)?
3. 閾値を広げた場合、副作用(床が「効きすぎる」ことで、コリドーが実際に
   狭まった正当な場面でも過去の高い床値に引きずられる、Fix Bの前提
   「コリドー実測は常に優先する」を壊さないか)をどう評価すべきか。
   Fix B自体は毎周期`corr_bound`で再キャップする設計(必ず
   `corr_bound - margin`以下に収まる)だが、この保護がスコープ拡大後も
   十分に機能するか確認したい。
4. 代替案として、「並走中」の定義を`state=="OVERTAKING"`全体(=側が
   確定してから離脱するまでの全期間)へ単純に広げてしまう案はどうか?
   これなら新規の距離閾値検討そのものが不要になるが、意図(並走中のみに
   限定してSTOPPING中の誤爆を防ぐ)を壊さないか、既存のFix Bの設計文書
   (§2.1)が想定していた「STOPPING/proactive-bias分岐でも同一ヘルパーを
   使う」設計との整合性はどうなるか。
5. 上記を踏まえて、Fix Bの再設計(閾値変更のみ、またはロジック自体の
   変更)を提案してほしい。

## 制約・注意事項

- 既存の安全設計(§0の多層防御方針、CLAUDE.md §1.3の慎重領域=switchback/
  rescue判定・cleared判定には触れない)は維持したい。
- Fix Bはconfigゲート`overtake.overlap_floor_enabled`(既定false)で
  既に既存挙動とビット等価な形で実装済み(コミット`3706a14`)。閾値変更は
  この既存実装への軽微な修正で済む想定(新規状態変数の追加は避けたい)。
- 段階導入方針(§10、Fix A'→B→Cを個別に検証してから次へ進む)を維持する。
  Fix Bがこのまま実効性のない状態でdev3/予選環境へ進んでも意味が
  ないため、このオフライン検証で立ち止まった。
